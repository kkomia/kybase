## 1. 这是什么、为什么存在

一句话：**kylab 的知识库剥离成独立服务，Agent 侧经窄 API / MCP / Skill 接入**；
Agent 在没有知识库时完整可用（降级而非失效）。

- 本仓库 `kybase` = 剥离出来的**知识库服务**（摄入流水线 / 混合检索 / Wiki / 表格副本 /
  账号体系 / MCP 对外面）。
- 源仓库 `kylab` = 留下的 **Agent 侧**（应用壳 + 边车 + 会话/笔记/记忆/技能/沙箱/工作区/
  定时任务/外部 MCP/备份）。

这条边界**不是新定的**：kylab 的 `docs/设计/架构设计-v0.3.md` §9 M3 验收原文就是
「**不配知识库时导航无 KB 页、Agent 全流程不受影响**」。本方案做的事，是把这条已验收的
**逻辑边界**落成**物理边界**（独立进程、库、镜像、仓库）。

### 3.3 Skill 文档修正（两处）

Skill 是**独立交付物**（规范 §6.3），它写给的是"只会 shell 与 HTTP 的别人的 Agent"，
所以文档里的每句事实都会被人照着做——这两处都是**照着做就会出错**的。

**第一处（2026-10-08）**：`skills/kylab-knowledge-base/README.md` 的「安全」一节原文说
「MCP 的 HTTP 模式**没有自己的鉴权**……它绕过后端那套账号/API Key 直接操作存储」，
「后端鉴权**保护不到**这条链路」。**这与现状矛盾**：读 kylab
`backend/app/mcp_server/auth.py` + `server.py` 确认，HTTP 模式自 v0.12 起**强制鉴权**——
中间件 `CallerMiddleware` 每个入站消息解析 `Authorization: Bearer <API Key>`（头名大小写不敏感），
stdio 走环境变量 `KYLAB_MCP_KEY`，**两者都没有则一律拒绝**（握手与 `tools/list` 仍放行，
真正的工具调用在 `call_tool` 里被 `current_caller()` 拒掉）；判定复用服务层同一套
`ApiKeyService`，不是另写一套。已按此改写那一节，并把"默认只监听 127.0.0.1"的理由
改成仍然成立的说法（**工具集里含删除**）。

> 注意：**鉴权这条上** `SKILL.md` 本来就是对的（"Every tool call needs a credential — there is no
> anonymous access"），**不用改**；两份文档此前是自相矛盾的，现在一致了。
> （`SKILL.md` 另有一处**数字**过时，是另一回事，见下一处。）

**第二处（2026-10-08 补做，收掉本文档 v0.1 的遗留 #1）**：`SKILL.md` 的 Local setup 里写
`python -m app.mcp_server.server --list-tools` 后面跟了一句
"confirm the **11 tools** are visible"。实测 `TOOL_NAMES`
（kylab `backend/app/services/tools.py:96-118`）是 **21** 个，这个数字早就过时了；
而 kylab `mcp_server/server.py:79-80` 的注释正是同一个口径——
「**别在这里写工具个数**：它随版本变（写"十一个"时已经涨到十六个），而一句过期的数字
会让读的人以为少挂了几个。个数以 `TOOL_NAMES` 为准」。已按该口径改成**不写死个数**的说法
（读它列出来的清单，不比对记忆里的数字）。kylab 侧原件**不动**（双份并存期，见 §3.4）。

### 3.4 双份并存期（重要）

`skills/kylab-knowledge-base/` 现在**两个仓库各有一份**，这是**有意**的：

- **kylab 侧原件保留不动**——那边的 Skill 还在被人用，删了就是断供；
- **kybase 侧这一份是新的归属地**（方案 §6 第 14 条：Skill 本来就是"会被安装到别处"的独立交付物，

并存期的纪律：

1. **kybase 侧这一份是线上那份**——服务已经跑在本仓的后端上，Skill 讲的服务就是它，
   所以要改就从这一份改起（kylab 侧原件还在，取它当年的历史时再对照）。
2. **只在 kybase 侧改**（如本次的两处文档修正）；改完记一笔，别指望 kylab 侧同步。
3. kylab 侧原件的**删除时点是方案 §6 第 13/14 条的"物理独立"阶段**，由那边定。
4. 并存期结束前，两边都会出现在各自的 `git log` 里，**不要互相当成对方的分支**。

## 4. 归属清单（浓缩版）

**完整清单看方案 §3，含逐文件点名。** 这里只给判据与最容易记错的几项。

### 4.1 一句话判据

- **知识库带走**：让"文档进来 → 变成可检索的东西 → 被检索出来"这条链路成立的全部代码、

- **Agent 留下**：对话、笔记、记忆、技能、插件、外部 MCP、沙箱、工作区、定时任务、
  应用壳与备份。
- **共享底座**：量小的纯契约与基础设施，先双拷贝、各自演化；归属见 §5。

### 4.2 KB 带走什么

| 域 | 带走的东西（概括） |
|---|---|
| REST | `/knowledge-bases` `/documents` `/folders` `/search` `/chunks` `/data-sources` `…/shares` `/wiki*` `/tabular` `/lifecycle` `/maintenance` `/tasks` `/webhooks` `/stats/dashboard` `/provider/handshake` `/chat/suggested-questions` |
| 服务 | 摄入/切块/解析路由/检索/嵌入/摘要/Wiki/表格(SQL)/连接器/分享/生命周期/维护/统计/Webhook/可观测性/建议问 |
| 解析器 | `parsers/` 全部（插件层，互不引用，零障碍） |
| 流水线 | `pipeline/state_machine.py`（摄入状态机） |
| 存储 | `postgres_impl/`（向量 + 全文 + KB 元数据）、`duckdb_impl/`（表格副本）；`split_impl/` 的历史使命结束，降级实现可留 Agent 侧 |
| 队列 | `workers/queue_worker.py`（摄入消费者） |
| MCP | `mcp_server/` 整体带走，**但只暴露 KB 工具**（见 §5 的「KB 的 MCP server 工具面」） |
| 账号 | `users`/`sessions`/`api_keys` + `auth`（见 §5 的「账号体系」） |

`conversations`/`chat`（Agent 链路）/`notes`/`memory`/`skills`/`plugins`/`mcp_servers`/`sandbox`/
`workspaces`/`schedules`/`web`/`site_icons`/`local` 这些路由与服务，
`agent.py` / `tool_loop.py` / `agent_tools.py` / `subagent.py` / `sandbox.py` / `command_policy.py` /
`skills*.py` / `plugins.py` / `mcp_client.py` / `workspace.py` / `notes.py` / `memory*.py` /
`conversation*.py` / `deck/` 等服务，`storage/sqlite_impl/`（本机库），`workers/local_worker.py`，
入口 `sidecar.py`，以及**备份全套**（见 §5 的「备份」）。

**前端只留两块 KB 相关界面**：应用壳与 `features/chat/`/`features/notes/` 等照旧，

### 4.4 共享底座怎么处

| 共享件 | 处置（已定，见 §5） |
|---|---|
| `core/`（exceptions / signing / page_markers / text_hygiene / http） | 纯契约，量小无业务语义——**先双拷贝**，稳定后再考虑抽内部包 |
| `core/config.py` | 切成三组引导配置：KB 引导 / Agent 引导 / 共享基础设施。**`data_dir` 是最大共享耦合点**，它派生出所有存储路径 |
| `storage/base.py` 的 `MetaStore` | 按 `LOCAL_METHODS` 切成 `KbMetaStore` / `LocalMetaStore` 两个窄接口（那份方法清单就是现成切分线） |
| `models/enums.py` | 各带一份 |
| `usage_events` / `idempotency_keys` / `app_settings` | 各带一份（无跨域语义） |
| `tasks` 队列表 | 随 KB（队列里 KB 摄入占绝对主体）；Agent 定时任务另起机制（本机 SQLite 已有落点） |

### 4.5 四条会绊人的事实

1. **跨域引用全是无外键的软引用**——`conversations.kb_ids`、`chat_messages.sources`（快照）、
   `notes.kb_id/doc_id`、`workspaces.kb_ids`、`scheduled_tasks.kb_ids`、
   `api_keys.knowledge_base_ids` 都是 jsonb/文本。**物理拆库不撞任何外键约束**，
   但必须定义「引用的库已不存在」的语义。
2. **Agent → KB 的进程内调用全仓只有一处**：`services/agent_tools.py:1263` →
   `services.chat.retrieve_sources(...)`。调用点不是问题，卡人的是**四个混合体文件 +
   一张混装宽接口**（方案 §4：第一刀必须切 `core/services.py`）。
3. **`user_id=None` 共享桶**：裸 API Key 建出来的资源没有归属人。若独立后要按用户隔离，
   协议上得补 owner 传递（方案 §7.2）。
4. **DuckDB 单文件单写者**：KB 服务若要多副本，表格副本层要先改造（方案 §7.3）。

### 5.1 前端形态：定案、变动与原因（唯一一条改了方案建议的决策）

**定案**（老板 2026-10-08）：

- 知识库页面**整体搬出 agent 产品**；`kybase` 自带**纯 web 管理台**（`kybase/frontend`），
  **不进桌面壳**——不作为 kylab Tauri 壳里的视图存在，也不依赖那个壳。
  形态名沿用方案的字母：这是**原方案 §5.4「形态 B」（KB 独立前端）的变体**，
  多加了「纯 web、不进壳」这条约束。
- kylab 前端**后续下线「知识库」页面群**：`features/knowledge/`、
  `features/misc/dashboard/`（`/stats/dashboard` 是 KB 的数据源）、`features/misc/tasks/`。
  只保留两块 KB 相关界面：
  1. **「知识库连接」设置**——KB 服务地址 / 测连 / API Key，这是 Agent 侧唯一的 KB 配置入口；
  2. **对话内的选库与引用展示**——`ComposerControls` 的选库、回答里的引用原文。
- 方案 §5.4 的**形态 A 不再是推荐口径**。A 是"同一个壳内两套前端"，本次定案与它相反：
  前端也在物理上分家。

**为什么改**（记录在案的四条）：

1. **形态 A 会把两个产品重新粘在一起。** A 的前提是同一个壳同时服务两边，于是 kylab 的壳、
   登录门禁、样式与构建链都会持续依赖 KB——与 §8 验收 2「Agent 在没有知识库时完整可用」方向相反。
2. **两套身份不该同居一个壳。** 账号体系随 KB（见上表），而桌面壳的登录/门禁是 Agent 侧逻辑；
   方案 §5.4 自己就点了"登录双档逻辑要表态"——分成两个仓库后，这个表态不必要了。
3. **发版解耦是一条独立收益。** 前端分家后两个仓库各自构建、各自发版，与阶段 4-2
   （KB 服务独立版本号）和 §8 验收 5（各自门禁全绿）一致。
4. **但不能因此不要前端。** 方案 §5.4 否决形态 C（纯 MCP、无前端）的理由依然成立且更关键：
   Wiki、库设置、分享、目录、处理时间线、检索分数展示**没有 MCP 工具对应物**——
   所以问题从来不是"要不要前端"，而是"前端放哪个仓库"。

**代价与要注意的**（方案 §5.4 登记的形态 B 难点，逐条继承）：

- `features/preview/` 两边都消费（KB 的 `DocumentDrawer` 与 Agent 的 chat 面板共用，
  且 `FilePreview.tsx:110` 反向引 `chat/model/markdown`）→ 现在**必须复制或抽包**，不能再"共用一份"；
- `src/ui/**`、`src/lib/*`、样式 token 层要抽包或复制（复制会漂，抽包得先立内部包）；
- `api/client.ts` 与 OpenAPI / 前端类型生成链跟着各自的域走（阶段 3-5）；
- 工作量比形态 A 大一个量级，**要与阶段 1/2 的后端切割并行推进**，不能压到最后（落点：阶段 3-6）。

## 1. 这是什么、为什么存在

一句话：**kylab 的知识库剥离成独立服务，Agent 侧经窄 API / MCP / Skill 接入**；
Agent 在没有知识库时完整可用（降级而非失效）。

- 本仓库 `kybase` = 剥离出来的**知识库服务**（摄入流水线 / 混合检索 / Wiki / 表格副本 /
  账号体系 / MCP 对外面）。
- 源仓库 `kylab` = 留下的 **Agent 侧**（应用壳 + 边车 + 会话/笔记/记忆/技能/沙箱/工作区/
  定时任务/外部 MCP/备份）。

这条边界**不是新定的**：kylab 的 `docs/设计/架构设计-v0.3.md` §9 M3 验收原文就是
「**不配知识库时导航无 KB 页、Agent 全流程不受影响**」。本方案做的事，是把这条已验收的
**逻辑边界**落成**物理边界**（独立进程、库、镜像、仓库）。

### 3.3 Skill 文档修正（两处）

Skill 是**独立交付物**（规范 §6.3），它写给的是"只会 shell 与 HTTP 的别人的 Agent"，
所以文档里的每句事实都会被人照着做——这两处都是**照着做就会出错**的。

**第一处（2026-10-08）**：`skills/kylab-knowledge-base/README.md` 的「安全」一节原文说
「MCP 的 HTTP 模式**没有自己的鉴权**……它绕过后端那套账号/API Key 直接操作存储」，
「后端鉴权**保护不到**这条链路」。**这与现状矛盾**：读 kylab
`backend/app/mcp_server/auth.py` + `server.py` 确认，HTTP 模式自 v0.12 起**强制鉴权**——
中间件 `CallerMiddleware` 每个入站消息解析 `Authorization: Bearer <API Key>`（头名大小写不敏感），
stdio 走环境变量 `KYLAB_MCP_KEY`，**两者都没有则一律拒绝**（握手与 `tools/list` 仍放行，
真正的工具调用在 `call_tool` 里被 `current_caller()` 拒掉）；判定复用服务层同一套
`ApiKeyService`，不是另写一套。已按此改写那一节，并把"默认只监听 127.0.0.1"的理由
改成仍然成立的说法（**工具集里含删除**）。

> 注意：**鉴权这条上** `SKILL.md` 本来就是对的（"Every tool call needs a credential — there is no
> anonymous access"），**不用改**；两份文档此前是自相矛盾的，现在一致了。
> （`SKILL.md` 另有一处**数字**过时，是另一回事，见下一处。）

**第二处（2026-10-08 补做）**：`SKILL.md` 的 Local setup 里写
`python -m app.mcp_server.server --list-tools` 后面跟了一句
"confirm the **11 tools** are visible"。实测 `TOOL_NAMES`
（kylab `backend/app/services/tools.py:96-118`）是 **21** 个，这个数字早就过时了；
而 kylab `mcp_server/server.py:79-80` 的注释正是同一个口径——
「**别在这里写工具个数**：它随版本变（写"十一个"时已经涨到十六个），而一句过期的数字
会让读的人以为少挂了几个。个数以 `TOOL_NAMES` 为准」。已按该口径改成**不写死个数**的说法
（读它列出来的清单，不比对记忆里的数字）。kylab 侧原件**不动**（双份并存期，见 §3.4）。

**本轮（2026-10-10 · 检索契约、失败语义与页码诚实性）**：七组改动，都是"把内部事实
如实交出去"这一类。**没有新环境变量、没有新 schema 迁移**（`SCHEMA_VERSION` 仍是 **19**，
`backend/app/storage/postgres_impl/schema.py` 一处核对）：

1. **工具面有了指纹**（`services/tools.py` 的 `surface_fingerprint()`：工具名 / 描述 /
   输入输出 schema / `TOOL_NAMES` 顺序的 sha256 前 12 位）。三个落点：`serverInfo.version`
   的 `<发版号>+mcp.<指纹>`、`--list-tools` 的最后一行、`GET /api/v1/tools` 的
   `surface_fingerprint`（管理台「接入」页的「工具」档显示并可复制）。**起因是一个真实的坑**：
   一个测试者在三次部署中间测过一次，客户端没有任何办法察觉契约变过——发版号一直是
   `0.1.0`，旧参数被白名单安静丢掉，表现成"服务端行为莫名其妙"。指纹就是给这件事的答案。
   **它是机读量，数值随契约变，本文不写死**；
2. **领域失败现在是失败**：`mcp_server/server.py` 的 `make_handler` 不再把
   `{"error": "…"}` 当成功文本返回，而是回一个 `isError: true` 的 `CallToolResult`
   （正文形状一个字没动，老解析器照旧能用）；同时把参数校验从 SDK 的签名推导手里拿回来
   （`_permissive_signature` + `pin_contract`）——缺参数、枚举写错现在是**我们的中文**，
   不再是 pydantic 的英文 dump。**但 `top_k` / `keep` / `min_score` / `per_doc` / `offset` /
   `limit` 六个调节量刻意继续容错**（垃圾值退回默认）；
3. **`search` 的判定可机读**：声明了 `outputSchema`，每次返回附一份 `structuredContent`
   （11 个键，含 `offset` / `next_offset` / `query` / `hits` / `surface_fingerprint`）。
   **它是同一批数据的另一种读法，不是摘要**：`query` 与 `hits` 逐条照搬（2026-10-10 补上，
   从前只搬判定与计数——按 schema 读的客户端拿不到任何原文，等于这次检索的成果丢了）。
   文本那份的形状与键序**一次都没改**——读它的是模型，键序就是阅读顺序；
4. **翻页 + `keep` 语义变更**：`search` 多了 `offset`，响应多了 `offset` / `next_offset`；
   **`keep` 从"这一轮一共几条"变成"一页几条"，`top_k` 从 20 抬到 50 并改成"一次能翻到的
   总量"**（封顶收敛后那份名单）。判定（`summary` / `distribution` / `decision`）在同一批
   候选的**每一页上逐字相同**。配套：`returned` 是这一页的条数，`kept`（与按库趋势里的
   `kept`）是收敛后剩下的总数、**不是某一页**，`dropped` / `filtered_out` 不再包含旧的
   `keep` 那一刀；`candidate_k` 小于 `top_k` 时被抬到 `top_k`；
   每条命中还多了 `basis`（`vector` / `fulltext`）与 `lexical_score`，`min_score`
   **只切向量通道**、绕过它的条数记在 `decision.unscored_kept`（"阈值提到 0.99 却回来一批
   `similarity: null`"的答案就是这个数）；
5. **页码改成"文档撑得住才给"**（`services/chunking.py` 的 `trusted_pages`）：只有当分页
   标记按 +1 递增、且末段标记等于文档页数时才给页码，否则该文档的块一律 `page = null`。
   `.md` / Office 类来源本来就没有页。**这是刻意的"宁缺勿错"**——一个翻不到原文的页码，
   比没有页码更糟（读者会从此不信任引用）。顺带修了大文件切段后相对页号没抬成绝对页号的
   问题（`core/page_markers.py` 的 `shift_page_markers` + `services/splitting.py`）。
   **存量数据不会自愈**，见 §9 遗留 #9/#10。
6. **读侧也如实说"这份产物的页码可不可信"**（`services/document_pages.py`）：
   入库侧那条规则（第 5 条）只管**新**数据，而**已经躺在库里的旧产物**读出来还是错的——
   2026-09-15..28 入库的那批切分文档，合并产物里 `<!-- page:1 -->` 反复出现，读侧只能照着
   把后面的正文全标成第 1 页。**实测**：`doc_a5e837b84bac`（Wills 眼科手册第 7 版，619 页）
   取第 1–2 页，回来的第 1 页正文从第 6 章一路铺到第 12 章；它的切块里只有 **19 个不同的
   `page` 值**、342 块中 **118 块标在 `page=1`**、`max(page)=200`（全库这类文档 **46 份**，
   其中 **21 份**是切分文档）。所以读侧新增一套判据（`page_marker_stats` 数出产物里的
   `(不同页号数, 最大页号)`，`PageReading` 把它与文档自称的 `page_count` 一起收拢，
   `read_pages` 收口、`_pages_reliable` 给判据）：`reliable` 三值——`None` = 没有页码可判
   （不是"页码错了"）/ `True` = 自洽（`max_page <= page_count` 且
   `pages_located * 2 >= page_count`；`page_count` 拿不到或 `<= 1` 也回 `True`，
   **没有依据就不喊狼来了**）/ `False` = 有页标记但对不上。对外两处都补了字段：
   REST `GET /documents/{id}/pages` 与 MCP `get_document_pages` 各多
   `pages_reliable` / `pages_located`，`false` 时 MCP 另给一条 `note`（说清两个数、
   说清**别拿那一段当「第 N 页」引用**、指向 `reparse_document`）；管理台「按页」档
   同一句小字。**文字照给**——不可信的是"它是第几页"，不是"它是不是这份文档的内容"。
7. **一个库的嵌入服务坏掉，只降级那个库**（`retrieval/service.py::_vector_channel`，
   配合 `mcp_server/server.py` 的边界）：**实测现场是 7 个库里 1 个用 WeMM、那个嵌入端点
   连不上，整次跨库检索全灭**（连"别的库查得到"那部分也没了），而且异常从工具边界逃出去，
   被 MCP SDK 压成一句没有细节的英文 `Error executing tool search`。两处修：① 边界同时
   认下 `KylabError` 与**刻意独立成一支**的 `EmbeddingError`（后者由嵌入提供方抛出、被
   ingest / retrieval / queue_worker 就地捕获，所以没并进前者），领域失败一律以
   `isError: true` + 中文原因回报；② 向量通道**逐个库**跳过失败的那个（**全文通道照旧
   参与召回**、别的库一切照常），并把 `{kb_id: 一句原因}` 记进
   `decision.embedding_unavailable_kbs`（**全部库正常时这个键不出现**；
   `EmbeddingNotConfiguredError`（没选模型）仍是静默跳过那条、不进名单）。
   **那半边已于 2026-10-10 解决（部署侧，不是代码）**：WeMM 那一档"连得上但不回"的真实成因
   不是端点慢，而是**接口地址登记成了容器不可达的 overlay 地址**——原先填的是 NAS 那套

   `http://192.168.31.18:8234` 后，容器内实测 2048 维向量正常返回、跨库检索 184 秒 → 1.2 秒

   overlay / Tailscale / `100.64.0.0-10` 段的地址**；口径与容器内探活命令见

### 5.1 前端形态：定案、变动与原因（唯一一条改了方案建议的决策）

**定案**（老板 2026-10-08）：

- 知识库页面**整体搬出 agent 产品**；`kybase` 自带**纯 web 管理台**（`kybase/frontend`），
  **不进桌面壳**——不作为 kylab Tauri 壳里的视图存在，也不依赖那个壳。
  形态名沿用方案的字母：这是**原方案 §5.4「形态 B」（KB 独立前端）的变体**，
  多加了「纯 web、不进壳」这条约束。
- kylab 前端**后续下线「知识库」页面群**：`features/knowledge/`、
  `features/misc/dashboard/`（`/stats/dashboard` 是 KB 的数据源）、`features/misc/tasks/`。

  1. **「知识库连接」设置**——KB 服务地址 / 测连 / API Key，这是 Agent 侧唯一的 KB 配置入口；
  2. **对话内的选库与引用展示**——`ComposerControls` 的选库、回答里的引用原文。
- 方案 §5.4 的**形态 A 不再是推荐口径**。A 是"同一个壳内两套前端"，本次定案与它相反：
  前端也在物理上分家。

**为什么改**（记录在案的四条）：

1. **形态 A 会把两个产品重新粘在一起。** A 的前提是同一个壳同时服务两边，于是 kylab 的壳、
   登录门禁、样式与构建链都会持续依赖 KB——与 §8 验收 2「Agent 在没有知识库时完整可用」方向相反。
2. **两套身份不该同居一个壳。** 账号体系随 KB（见上表），而桌面壳的登录/门禁是 Agent 侧逻辑；
   方案 §5.4 自己就点了"登录双档逻辑要表态"——分成两个仓库后，这个表态不必要了。
3. **发版解耦是一条独立收益。** 前端分家后两个仓库各自构建、各自发版，与阶段 4-2
   （KB 服务独立版本号）和 §8 验收 5（各自门禁全绿）一致。
4. **但不能因此不要前端。** 方案 §5.4 否决形态 C（纯 MCP、无前端）的理由依然成立且更关键：
   Wiki、库设置、分享、目录、处理时间线、检索分数展示**没有 MCP 工具对应物**——
   所以问题从来不是"要不要前端"，而是"前端放哪个仓库"。

**代价与要注意的**（方案 §5.4 登记的形态 B 难点，逐条继承）：

- `features/preview/` 两边都消费（KB 的 `DocumentDrawer` 与 Agent 的 chat 面板共用，
  且 `FilePreview.tsx:110` 反向引 `chat/model/markdown`）→ 现在**必须复制或抽包**，不能再"共用一份"；
- `src/ui/**`、`src/lib/*`、样式 token 层要抽包或复制（复制会漂，抽包得先立内部包）；
- `api/client.ts` 与 OpenAPI / 前端类型生成链跟着各自的域走（阶段 3-5）；
- 工作量比形态 A 大一个量级，**要与阶段 1/2 的后端切割并行推进**，不能压到最后（落点：阶段 3-6）。

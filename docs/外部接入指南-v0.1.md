## 1. 能力概览

### 1.1 这个服务给什么

一句话：**带出处的原文检索**。

- 检索返回的是**你文档里的原文片段**（含文档名、页码、标题路径），
  **不是生成的回答**。这是产品的主打能力，也是它存在的理由——
  需要**核对**答案时，原文是证据，摘要不是。
- 服务端**不做任何 LLM 预处理**：请求就是检索，返回就是片段
  （提示注入防护的责任在调用方）。
- 文档进库后经过解析、切分、向量化、索引，之后同时支持
  向量 / 全文 / 混合三档检索，并带重排与元数据过滤。

### 1.2 不给什么（边界）

| 不提供 | 说明 |
|---|---|
| 生成式问答 | 服务端不自带对话链路；要"一段连贯的话"请在你自己的 Agent 里拿片段合成 |
| 匿名访问 | **鉴权永远生效，没有开关**。缺凭据一律 401 |
| 管理员能力（对 API Key） | API Key 拿不到设置、模型凭据、用户与 API Key 管理那一族（403） |
| Agent 侧能力 | 笔记正文、记忆、会话、沙箱、联网搜索属于 **Agent 域**，不是知识库服务对外面（见 §1.3 末尾） |

### 1.3 四条接入路径

| 路径 | 给谁 | 协议 | 本文 |
|---|---|---|---|
| **MCP** | 支持 MCP 的客户端（Claude Desktop、Cursor 等） | stdio / Streamable HTTP | §3 |
| **REST（OpenAPI）** | 任何会说 HTTP 的程序 | `/api/v1/**`，OpenAPI 3 | §4 |
| **官方 Skill** | 装在别的 Agent 里的技能包（内含一个纯 REST 脚本） | 目录 + `SKILL.md` | §5 |
| **窄 API（provider 握手）** | 想把知识库**内嵌**进自己主链路的 Agent | `GET /provider/handshake` + 既有 KB REST | §6 |

三条对外的路（MCP / REST / Skill）**能力等价、服务端同源**，选一条即可，不必都接。

> **注意"MCP 工具表"的边界**：kylab 单体当年挂的是**整张工具表**
> （`TOOL_NAMES`，21 个），其中 10 个是知识库工具，另外 11 个是 Agent 侧工具
> （笔记、记忆、联网、导出）。**kybase 的 MCP server 只暴露纯知识库工具**：
> 2026-10-09 的后端瘦身把 Agent 侧那 11 个实现整体拆掉，也把 `attach_note_to_kb` /
> `ingest_artifact` 两个跨域工具一并删了（源对象是 Agent 侧的笔记与产物），
> 于是 `TOOL_NAMES` 就剩 §9.1 那张表——**对外面就是这张表本身**，
> 不再有"按白名单过滤出的子集"这一层。**个数以 `TOOL_NAMES` 为准，本文不写死**：
> 2026-10-09 之后又加了 `get_document_content`（§3.6）。

## 2. 获取凭据

### 2.1 两种凭据

按**前缀**分流，走两条不同的校验路径：

| 凭据 | 前缀 | 谁用 | 能做什么 |
|---|---|---|---|
| **API Key** | `kylab_sk_…` | 外部程序、外部 Agent | 只读或读写，**可限定知识库范围、也可限定工具范围**（§2.3）；碰不到服务端凭据 |
| **登录会话令牌** | `kylab_st_…` | 浏览器控制台 | 全部业务；`role=admin` 还能读写设置 / API Key / 用户 |

- 两种凭据**在 REST 与 MCP 里都能用**（同一套判定，不是两套）。
- **管理员身份不能由 API Key 兼任**：设置页是 embedding / LLM 密钥的落点，
  地址可改——给了外部 API Key 就等于给它一条"把你的凭据转发到我的服务器"的路。
- 明文只在**创建那一次的响应里**出现；库里只存 SHA-256 哈希。

### 2.2 在哪儿建一把 API Key

界面路径：**控制台侧栏「API 密钥」页 → 新建**。这一页 2026-10-09 从账号菜单里搬出来，
成了侧栏上独立的一页（路由 `/api-keys`）——**账户菜单里那张"设置 → API 密钥"已经不在了**，
照着旧文档点只会找不到入口。

程序路径（需要管理员会话令牌，不是 API Key）：

```bash
curl -sS -X POST "$KB_BASE/api-keys" \
  -H "Authorization: Bearer kylab_st_<管理员会话令牌>" \
  -H 'Content-Type: application/json' \
  -d '{"name":"外部接入-只读","permission":"readonly",
       "knowledge_base_ids":["kb_xxx"],
       "allowed_tool_names":["search","list_knowledge_bases"]}'
```

响应 `201`，`token` 字段就是明文（**唯一一次**，抄下来存好）。其余字段：
`id` / `name` / `permission` / `knowledge_base_ids` / `allowed_tool_names` /
`created_at` / `last_used_at` / `prefix`。
三个 API Key 端点（列表 / 新建 / 撤销）**都要管理员会话**，API Key 自己调它们一律 `403`——
**只有这三个**：没有"改一把已有 Key"的端点，改范围（库或工具）只能**撤销后重发**。

### 2.3 只读 / 读写，与绑库范围、绑工具范围

| 字段 | 取值 | 语义 |
|---|---|---|
| `permission` | `readonly`（**默认**）/ `readwrite` | 只读档做写操作 → `403`，文案指明"该 API Key 只有只读权限" |
| `knowledge_base_ids` | 列表 | 空列表 = **不限范围**（可访问全部库）；非空 = 只能碰这些库 |
| `allowed_tool_names` | 列表 | 空列表 = **不限工具**；非空 = 只能调这几个 MCP 工具（名字见 §9.1 的工具表，或 §4.4 的 `GET /tools`） |

- 默认值刻意取**最保守**的那一档：给外部集成发一把能删库的钥匙，
  不该是因为"没填那个字段"。
- **越权回 `403`，不是"空的检索结果"**——范围外与"库里没有"必须能分开，
  否则你会把权限问题当成内容问题查很久。
- 越权报错会**点名是哪个库**（库 id 不是秘密，列表接口本来就能看到）。
- 只读 Key 能做的：列库、列文档、查状态、取正文（`get_document_content`）、检索。
  不能做的：建库、上传、加数据源、删文档。
- **工具范围只作用于"工具面"**：MCP 的全部工具，以及 REST 上与某个工具一一对应的
  那几个端点——`POST /search`、`GET|POST /knowledge-bases`、`GET|POST
  /knowledge-bases/{kb_id}/documents`、`POST /knowledge-bases/{kb_id}/documents/batch`、
  `GET|DELETE /documents/{document_id}`、`POST /knowledge-bases/{kb_id}/data-sources`，
  以及取内容那两条 `GET /documents/{document_id}/preview` 与
  `GET /documents/{document_id}/download-url`（它们在 REST 上就是 `get_document_content`
  的两个入口）。表外的 REST 端点（库详情、改名、移动、任务、统计、分享……）仍然只看
  `permission` 与 `knowledge_base_ids`——**工具范围不是第二套权限系统**。
- 工具范围也管 MCP 的 `tools/list`：限了范围的钥匙**只看得到它调得动的那些工具**，
  范围外的连列都不列——摆出来再拒，只会让模型对着一个永远调不成的工具反复试。
- 建钥匙时写一个不存在的工具名会**当场 `422`**（不会静默存下来），报错里会列出可用的名字。

### 2.4 什么时候该用会话令牌

需要**归属（owner）**时。API Key 通道没有账号，用它建出来的资源没有主人
（知识库 `owner_id`、文档 `uploaded_by` 都是 `NULL`）——而"能不能管这个库"
（`can_manage`，含分享）的判据正是**拥有者或管理员**，无主库只有管理员管得了。所以：

- 只是**检索**：API Key 足够（只读档即可）。
- 要**替某个用户写入**（把库 / 文档挂在那个用户名下）：用那个用户的会话令牌。

### 2.5 凭据的已知边界（照实说）

- **API Key 没有有效期**。当前只能"撤销后重发"来轮换，没有过期时间字段。
- 凭据不可回显：所有查询接口只回"配没配"与掩码尾巴，明文丢了只能重建。
- 撤销：`DELETE /api/v1/api-keys/{key_id}`（回 `204`，需管理员会话）。

## 3. 接入路径 A：MCP

### 3.1 两种传输，同一批工具

| 传输 | 场景 | 凭据来源 |
|---|---|---|
| **stdio** | 本地客户端把服务当子进程拉起 | 客户端配置里的环境变量 `KYLAB_MCP_KEY` |
| **Streamable HTTP** | 别的机器经网络连过来 | 每个请求的 `Authorization: Bearer <凭据>` |

两者的差别只在"消息怎么走"，工具集与实现**完全共用**。

**鉴权是强制的**，规则如下（照抄，别自己发明）：

1. **两者都没有凭据** → 握手与 `tools/list` **仍然放行**（否则客户端连不上、
   排障时一点线索都没有），但**每一个工具调用都会被拒**，并说明缺哪份凭据。
2. **凭据存在但无效** → 中间件**立刻拒绝**（配置错了，越早说清越好）。
3. 头名**大小写不敏感**——`authorization` 也认。

### 3.2 stdio 配置片段

```json
{
  "mcpServers": {
    "kybase": {
      "command": "python",
      "args": ["-m", "app.mcp_server.server", "--transport", "stdio"],
      "cwd": "/absolute/path/to/kybase/backend",
      "env": { "KYLAB_MCP_KEY": "kylab_sk_<你的 API Key>" }
    }
  }
}
```

- `cwd` 必须是**装了本服务的 backend 目录**，且该环境要装得上可选依赖 `mcp>=2`
  （MCP 是可选能力，没装 `mcp` extra 时主服务照常起）。
- 服务进程用的是**服务端自己的配置**（数据库连接串、对象存储、数据目录）——
  它与 HTTP 那一路是同一个进程配置，不是客户端本地库。部署方会给你这些。
- **stdio 那条传输没有请求头可读**，所以凭据只能来自环境变量，这是唯一来源。

### 3.3 Streamable HTTP 配置片段

**NAS 上那套已经起着**（`deploy/nas/docker-compose.yml` 的 `mcp` service，独立的容器，
与后端同镜像、换入口命令），地址是 `http://192.168.31.18:8765/mcp`。要自己起，或看它怎么起的：

```bash
python -m app.mcp_server.server --transport http --host 0.0.0.0 --port 8765
```

客户端配置（字段名随客户端而异，`url` + 自定义头是通用部分）：

```json
{
  "mcpServers": {
    "kybase": {
      "type": "http",
      "url": "http://<kybase-host>:8765/mcp",
      "headers": { "Authorization": "Bearer kylab_sk_<你的 API Key>" }
    }
  }
}
```

> 上面 `url` 里的 `http://192.168.31.18:8765/mcp` 就是今天那台的实际值。

三条要记住的：

1. **默认只监听 `127.0.0.1`**——MCP 能读**也能删**知识库。要让别的机器连，
   必须显式传 `--host 0.0.0.0`，并且只放在可信网络里。
2. 端点路径是 MCP SDK 的默认值 **`/mcp`**（本项目没有覆盖它）。
3. **默认端口 `8765` 与 kylab 桌面边车抢用的端口段（8765–8769）重合**。
   同一台机器上同时跑两者时，其中一方要显式换端口（NAS 上那套用的就是 `8765`，
   与它抢段的桌面边车不在同一台机器上）。

### 3.4 自检（先确认"装上了、工具认得出来"）

```bash
cd /absolute/path/to/kybase/backend
python -m app.mcp_server.server --list-tools   # 只打印工具清单，不启动服务
```

`--list-tools` 打印的是**当前的**工具清单：**读它列出来的，别比对记忆里的个数**
（工具集随版本增长，写死的数字早晚是错的）。其余命令行开关：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--transport` | `stdio` | `stdio` / `http` |
| `--host` | `127.0.0.1` | http 模式监听地址 |
| `--port` | `8765` | http 模式监听端口 |
| `--list-tools` | — | 只打印工具清单 |

### 3.5 调用时的三个行为要知道

- **参数白名单**：每个工具只接受它 schema 里点名的参数，**schema 之外的参数被丢掉**
  （不是报错）。所以传错名字的参数表现为"这个参数没起作用"，请按 §9 的表对齐参数名。
- **白名单与 schema 今天有一处不一致，以白名单为准**：`search` 的 schema 里声明了
  `keep` / `min_score` / `per_doc`（描述里也让模型用它们收敛条数），但
  `server.py` 的 `_PARAMS["search"]` 只列出了 `query` / `knowledge_base_ids` / `top_k`
  ——**这三个参数在 MCP 通道上会被丢掉、不起作用**。想按分布收敛条数，要么用
  `top_k`，要么走 REST（那边对应的是 `score_threshold` / `min_vector_score` /
  `min_term_coverage`，名字不同、语义更直接）。这条已登记，见 §10。
- **领域错误不抛出，而是回一段 JSON 文本**：工具返回体里出现 `{"error": "缺少参数：filename"}`
  这类形状时，是**业务失败**（不是协议失败），要读 `error` 字段——
  这样模型 / 客户端能自己把参数改对，或把原因转述给你。

### 3.6 取一份文档的全文：`get_document_content`

`search` 只回**与问题相关**的片段；要**通读全文**或核对原文版式时用它。两个参数：
`document_id`（必填）与 `format`（`markdown` 默认 / `original`）。

**`format="markdown"`**（默认）——解析后的正文，检索依据的就是它：

```jsonc
{
  "document_id": "doc_xxx",
  "name": "近视防控手册.pdf",
  "format": "markdown",
  "media_type": "text/markdown; charset=utf-8",
  "filename": "近视防控手册.md",          // 解析产物按"原名去后缀 + .md"命名
  "size_bytes": 18422,
  "text": "# 第一章 眼轴\n\n眼轴长度是……",
  // 只在配了 KYLAB_PUBLIC_BASE_URL 时出现（见 §3.7）
  "download_url": "http://192.168.31.18:8081/api/v1/documents/doc_xxx/content?format=markdown&expires=…&signature=…"
}
```

**`format="original"`**——原文件本身，base64 放在 `base64` 字段（要原始版式时用，
它连同 `filename` / `media_type` / `size_bytes` 一起给你，够你落盘）：

```jsonc
{
  "document_id": "doc_xxx", "name": "近视防控手册.pdf", "format": "original",
  "media_type": "application/pdf", "filename": "近视防控手册.pdf",
  "size_bytes": 2388491, "base64": "JVBERi0xLjQK…"
}
```

两条**边界**都在返回值里体现，不靠猜：

| 情况 | 它怎么表现 | 你要做什么 |
|---|---|---|
| 正文超过 **20 万字符** | 只回前 20 万字符，并多一个 `"truncated": true` | **它不是全文**——被截掉的那半里可能正有你要找的东西，别据此说"文里没有"。要全量就按 `download_url` 取 |
| 原文件超过 **32MB** | **不回内容**：回一段领域错误（`{"error": "内容超过 32MB…请改用 REST 下载接口…"}`） | 走 §9.2 的 `GET /documents/{document_id}/download-url`，或返回体里那条 `download_url` |

- **读得到 ≠ 该拿它当默认**：整篇塞进上下文既装不下也读不完；"这份文档说了什么"这类
  问题仍应先用 `search` 定位相关段落，只有当片段不够、要核对原文时才整份取。
- **有没有 `truncated` 是判据**：没有这个键才是完整正文；有，就只是前一段。
- 权限与 `search` 同源：越权 `403`；**工具范围**里没勾它的 Key，调用会被拒——
  REST 那两条入口（`/preview`、`/download-url`）走同一个闸门。

### 3.7 两个只有部署方才知道的地址（`KYLAB_PUBLIC_BASE_URL` / `KYLAB_MCP_PUBLIC_URL`）

服务端**不猜对外地址**：签名链接是相对路径，工具目录里的 MCP 地址也不拼——这两处都只有
部署那一刻才知道。两个**可选**环境变量就是那个答案（`backend/.env.example` 里有模板）：

| 变量 | 形如 | 配了会怎样 | 留空会怎样 |
|---|---|---|---|
| `KYLAB_PUBLIC_BASE_URL` | `http://192.168.31.18:8081` | `get_document_content` 的返回体里多一条**绝对**的 `download_url`，可直接点开 / 下载 | **只是没有这一项**——其余字段照旧。降级，不报错 |
| `KYLAB_MCP_PUBLIC_URL` | `http://192.168.31.18:8765/mcp`（**整条**） | `GET /api/v1/tools` 的 `mcp_endpoint` 回这条地址（管理台「工具」页据此显示接入地址） | `mcp_endpoint` 为 `null`：**不猜、不拼**，界面照实说没配 |

- **为什么是两个**：REST 与管理台在 **8081**，MCP 是**另一个监听、另一个端口**（默认 **8765**），
  也可能落在两个域名后面。拿 REST 基址拼一条 `<基址>/mcp`，摆出来的就是一条**端口错**的地址，
  而照着它连的表现是"服务在跑却连不上"——最难排的一类。
- **都留空不影响任何功能**：只影响"链接点不点得开"与"界面上显不显示接入地址"。
- `download_url` 还多一个前提：**签名密钥存在**（`KYLAB_URL_SIGNING_SECRET`，或首次
  `POST /auth/setup` 自动生成的那条）。缺它同样只是没有这一项，不报错。

## 4. 接入路径 B：REST（OpenAPI）

### 4.1 基本约定

| 项 | 约定 |
|---|---|
| 前缀 | `/api/v1`。**路径即版本**，没有 header 版本协商 |
| 机器可读契约 | `GET /api/v1/openapi.json`；交互文档 `GET /api/v1/docs` |
| 时间 | 一律 ISO 8601 带时区，字段名以 `_at` 结尾；服务端内部按 UTC 存 |
| 分页 | `limit` + `offset`，列表回 `total`；`limit` 有服务端上限，超限回 `422` 而**不静默截断** |
| 探测 | `GET /api/v1/health` **不鉴权**（容器编排用），只回版本与存活 |
| 错误 | 所有非 2xx 都是同一个信封，见 §8 |

### 4.2 十分钟：一次检索

```bash
KB_BASE='http://<kybase-host>:<port>/api/v1'
KB_KEY='kylab_sk_<你的 API Key>'

# 0) 服务在不在（不鉴权）
curl -sS "$KB_BASE/health"

# 1) 先列库：拿到 kb id，并看自己能不能写
curl -sS "$KB_BASE/knowledge-bases" -H "Authorization: Bearer $KB_KEY"
# → {"items":[{"id":"kb_xxx","name":"产品手册","can_write":true,...}]}

# 2) 检索（kb_ids 必填且非空，见下方"三个必知"）
curl -sS -X POST "$KB_BASE/search" \
  -H "Authorization: Bearer $KB_KEY" -H 'Content-Type: application/json' \
  -d '{"query":"眼轴怎么监测","kb_ids":["kb_xxx"],"top_k":5}'
```

响应（节选）：

```json
{
  "hits": [
    {
      "chunk_id": "chk_xxx",
      "document_id": "doc_xxx",
      "document_name": "近视防控手册.pdf",
      "knowledge_base_id": "kb_xxx",
      "text": "……原文片段……",
      "score": 0.0328,
      "similarity": 0.71,
      "page": 12,
      "heading_path": "第三章 · 监测",
      "image_ids": [], "channels": ["vector", "fulltext"], "ranks": {"vector": 1}
    }
  ],
  "mode": "hybrid", "reranked": false, "filtered_out": 3,
  "embedding_configured": true, "embedding_is_development": false,
  "stats": []
}
```

**三个必知**：

1. **`kb_ids` 是必填且不能为空数组**（`min_length=1`）。想"查全部库"要先
   `GET /knowledge-bases` 把 id 全列出来再传——这是与 MCP 的 `search` 不同的一处
   （MCP 那边留空表示"查这个调用者能看到的全部库"）。
2. **`score` 不是相似度**，是融合分（RRF 家族，量级 `1/(k+rank)`）：向量档第 1 名恒为
   `0.0164`、hybrid 档第 1 名恒为 `0.0328`——它随名次走，不随"像不像"走。
   要看相似度读 **`similarity`**（真实余弦，`null` 表示只被全文通道捞到）。
3. **空结果不是错误**，但要分清三件事：库是空的 / 文档还没处理完 / 真的没有这份资料。
   先看 §7.1。

**常用检索参数**（完整类型见 `/docs`）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `query` | 必填 | 自然语言即可 |
| `kb_ids` | **必填、非空** | 在哪些库里查 |
| `top_k` | 8 | 上限 100 |
| `mode` | `hybrid` | `hybrid` / `vector` / `fulltext` |
| `candidate_k` | 40 | 上限 500 |
| `rerank` | false | 重排 |
| `score_threshold` | — | **相对**融合分下限（该条分 / 最高分），只剪尾巴 |
| `min_vector_score` | — | 向量余弦的**绝对**下限；不传则按库的嵌入模型用标定默认，`0` = 关闭 |
| `min_term_coverage` | — | 词面覆盖下限；不传则跟向量下限走，`0` = 关闭 |
| `filters` | — | 元数据过滤（`document_ids` / `source_kinds` / `created_after` / `created_before`） |

### 4.3 从零到可检索（建库 → 上传 → 轮询）

空库检索不到东西，所以完整闭环是这样（需要一个**读写**档的 Key）：

```bash
# 1) 建库（需要读写档）
KB_ID=$(curl -sS -X POST "$KB_BASE/knowledge-bases" \
  -H "Authorization: Bearer $KB_KEY" -H 'Content-Type: application/json' \
  -d '{"name":"外部接入试跑"}' | python -c 'import sys,json;print(json.load(sys.stdin)["id"])')

# 2) 上传（multipart，202 = 已受理，处理是异步的）
curl -sS -X POST "$KB_BASE/knowledge-bases/$KB_ID/documents" \
  -H "Authorization: Bearer $KB_KEY" \
  -F 'file=@./试用文档.md'
# → {"document":{"id":"doc_xxx","stage":"uploaded",...},"is_duplicate":false,"task_id":"..."}

# 3) 轮询进度，直到能检索（阶段名见 §7.1）
curl -sS "$KB_BASE/documents/doc_xxx" -H "Authorization: Bearer $KB_KEY"

# 4) 能检索了再查
curl -sS -X POST "$KB_BASE/search" \
  -H "Authorization: Bearer $KB_KEY" -H 'Content-Type: application/json' \
  -d "{\"query\":\"试跑\",\"kb_ids\":[\"$KB_ID\"]}"
```

**上传接口的完整形状**：

| 项 | 说明 |
|---|---|
| 方法 / 状态码 | `POST /knowledge-bases/{kb_id}/documents`，成功回 **202 Accepted** |
| 请求体 | `multipart/form-data`，字段名 `file` |
| 查询参数 | `start`（默认 `true`；`false` = 只登记不入队）、`folder_id`（可选，放进库内目录） |
| 请求头 | `Idempotency-Key`（**可选**）、`X-Kylab-Operator`（可选，**不参与鉴权**，只记录"是谁传的"） |
| 响应 | `{"document": {...}, "is_duplicate": bool, "task_id": "..."}` |
| 去重 | 按**内容 hash**：同一份内容重复上传回 `is_duplicate=true`，不会入两份 |
| 大小 | 超上限回 `413 payload_too_large`（切分 / 压缩再试） |

`Idempotency-Key` 是**可选**的，四种结果务必分清（上传本来就有内容 hash 兜底，
幂等键解决的是"客户端重试"那一小类场景）：

| 情况 | 结果 |
|---|---|
| 首次使用该键 | 正常处理 |
| 重放（键相同、请求体也相同） | 返回**上次的响应**（不重新处理） |
| 键相同但请求体不同 | `409`（要看 `code`） |
| 键相同、上次还在处理中 | `409`（不是 500，也不是空响应） |

键保留 24 小时，由后台空闲维护清理。

### 4.4 其他常用 KB 端点（速查见 §9）

- 库管理：`GET/POST /knowledge-bases`、`GET/PATCH /knowledge-bases/{id}`、
  `DELETE /knowledge-bases/{id}`（不可恢复）
- 文档：列表 `GET /knowledge-bases/{kb_id}/documents`、详情 `GET /documents/{id}`、
  时间线 `GET /documents/{id}/timeline`、重跑 `POST /documents/{id}/reprocess`、
  取消 `POST /documents/{id}/cancel`、停用 `PATCH /documents/{id}/disabled`、
  删除 `DELETE /documents/{id}`（进回收站）
- 切块：`GET/PATCH /documents/{id}/chunks`、`/documents/{id}/chunks/by-ordinal/{ordinal}`
- 数据源：`GET/POST /knowledge-bases/{kb_id}/data-sources`、
  `POST /data-sources/{id}/sync`（`wait=true` 立刻做完）
- 回收站：`GET /trash`、`POST /trash/{id}/restore`、`DELETE /trash/{id}`
- 取内容：`GET /documents/{id}/preview`（阅读视角——有解析产物就给 Markdown 文本，
  否则给原件版式的签名链接）、`GET /documents/{id}/download-url`（**签发**一条带签名的
  短期链接，`format=original`（默认）/ `markdown`）。这两条与 MCP 的
  `get_document_content` 是一回事，同一个工具范围闸门（§2.3）。
- 对外能力目录：`GET /tools`——工具清单（`name` / `label` / `summary` / `requires_write` /
  `params`）+ 随附技能（`skill`）+ 配好的 MCP 地址（`mcp_endpoint`，没配就是 `null`，见 §3.7）。
  只读档即可读，且**它回的是"这个服务有什么"，不是"你能用什么"**——限了工具范围的钥匙
  也看得到全量目录；能不能调由调用那一刻判。
- Wiki / 分享 / 表格 / 统计 / Webhook / 任务：`/wiki*`、`…/shares`、`/table`、
  `/stats/dashboard`、`/webhooks`、`/tasks*`

> 库列表回的是 `{"items":[...]}`（**没有 `total`**，库列表不分页）；
> 文档列表回 `{"items":[...], "total":n, "limit":.., "offset":..}`。

## 5. 接入路径 C：官方 Skill

Skill 是**独立交付物**，写给"只会 shell 与 HTTP 的别人的 Agent"。

**位置**：本仓 `skills/kylab-knowledge-base/`，三件东西：

| 文件 | 作用 |
|---|---|
| `SKILL.md` | 技能正文：工作流、工具用途、回答纪律、配置片段 |
| `README.md` | 中文说明：两条路径、快速自检、三个容易踩的点、安全 |
| `scripts/kylab_query.py` | 纯 REST 查询脚本（不依赖 MCP），打印原文片段 |

**安装**：把整个目录放进你的 Agent 的技能目录即可（各 Agent 的目录位置不同，
本服务不规定）。`SKILL.md` 里的路径与地址已按 kybase 现实改准（2026-10-09）：
stdio 场景写的是**在 kybase 仓的 `backend` 目录下**跑，HTTP 场景指向这台机器上的
`http://192.168.31.18:8765/mcp`（并保留"别的部署以部署方给的为准"）——见 §10 第 6 条。

**用脚本跑通一次检索**（不需要任何 MCP 客户端）：

```bash
export KYLAB_BASE_URL='http://<kybase-host>:<port>/api/v1'   # 脚本默认 http://127.0.0.1:8000
export KYLAB_API_KEY='kylab_sk_<你的 API Key>'                # 只读档即可

python scripts/kylab_query.py --list                          # 有哪些库
python scripts/kylab_query.py --query "眼轴怎么监测"           # 检索并打印原文
python scripts/kylab_query.py --query "…" --kb kb_xxx --top-k 8
python scripts/kylab_query.py --query "…" --json               # 给程序读
python scripts/kylab_query.py --query "…" --token "$KYLAB_API_KEY"
```

脚本的行为（接之前知道这几点，排障省很多时间）：

- **退出码**：`0` 成功（**包括零命中**——那是一个有效结论）、`1` 用法 / 传输错误、
  `2` 需要凭据（`401` / `403`）。`2` 单独成一档，是因为它是你唯一能改的一档，
  否则很容易被当成"没搜到"。
- 不传 `--kb` 时它**先列全部库再把 id 传进去**（对应 §4.2 的"`kb_ids` 必填"）；
  **一个库都没有时会明说"还没有任何知识库"**，而不是回一句"没搜到"。
- `--base-url` 默认 `http://127.0.0.1:8000`，**不含 `/api/v1`**（脚本自己拼）。

## 6. 窄 API：`GET /provider/handshake`（Agent 内嵌接入）

这条路是给**把知识库内嵌进自己主链路**的 Agent 用的：开机后先握手一次，
一次调用回答三件事——**凭据有效吗、这台提供者能做什么、我能用哪些库**。

> 它不是"另一套 API"：**窄 API = 既有的知识库 REST 族 + 这一个新增端点**。
> 检索、入库、进度、库管理用的还是 §4 那些端点。

### 6.1 调用

```bash
curl -sS "$KB_BASE/provider/handshake" -H "Authorization: Bearer $KB_KEY"
```

- **鉴权**：登录会话或 API Key 都行（**它只要只读**）。
- **凭据错是 `401` / `403`（→ 去改钥匙），连不上是超时 / 连接被拒（→ 去改地址）**。
  客户端必须把这两档**分开说**——混成一句"连不上"会让人白跑一趟。
  所以"凭据有问题"**不进响应体**，它由 HTTP 状态码 + 统一错误信封表达。

### 6.2 响应结构

| 字段 | 说明 |
|---|---|
| `provider` | 固定 `knowledge`（将来有别的提供者时用它分流） |
| `protocol_version` | 整数、**只增**，当前 `1` |
| `app_version` / `api_version` | 服务端应用版本 / HTTP 路径版本（`v1`） |
| `capabilities.retrieval` | `modes` / `default_mode` / `rerank` / `filters` / `top_k_max` / `candidate_k_max` |
| `capabilities.ingest` | `transport`（`multipart`）/ `async` / `dedup`（`content_hash`）/ `max_bytes` / `extensions` |
| `capabilities.tracking` | `document` / `timeline` |
| `capabilities.knowledge_bases` | `create` / `delete` / `folders` / `shares` / `wiki` |
| `capabilities.embedding` | `configured` / `is_development` / `model_id` / `dim` |
| `caller` | `kind`（`session` / `api_key`）/ `permission` / `is_admin` / `can_write` / `knowledge_base_ids` |
| `knowledge_bases[]` | `id` / `name` / `document_count` / `last_activity` / `can_write` / `embedding_model_id` / `embedding_dim` / `wiki_enabled` |
| `server_time` | 服务端当前时间（UTC，带时区） |

### 6.3 客户端必须遵守的四条

1. **`protocol_version` 不认识（大于你已知的）即判不可用**，原因句子里带版本号，
   **绝不硬试**——拿新协议当旧协议发请求，会把语义错误显示成网络故障。
2. **`capabilities` 报的是"这台机器现在能做什么"**，不是"代码支持什么"：
   `embedding.configured=false` 时**仍然能上传**，只是检索拿不到向量通道；
   `ingest.max_bytes` / `ingest.extensions` 是**界面该照抄的那一份**
   （上传上限与格式提示不再各写一处）。
3. **`caller.is_admin` 如实报**。API Key 在提供者这一侧**不是管理员**，
   管理员专属端点对它一律 `403`——据此**隐藏**那些入口，而不是摆出来等着失败。
4. **`knowledge_bases` 只含这次调用看得见的库**（受限 Key 只看到范围内的），
   每项 `can_write` 与 `GET /knowledge-bases` 同一个判据。

## 7. 核心概念与坑

### 7.1 摄入是异步的，**没处理完就搜不到**

上传 / 入库**立刻回 202 + `document_id`**，解析、切分、向量化、索引在服务端队列里跑。
主链路阶段依次是：

```
uploaded → probing → parsing → parsed → chunking → chunked → embedding → indexed
```

另有可选增强分支 `enriching → enriched`（默认关闭，失败不影响主链路），
以及两个异常态 `failed` / `canceled`（都可以重新摄入，不是"坏掉了"）。

**"能不能搜到"的正确判据不是 `stage == indexed`，而是"有没有落库的切块且没被停用"**：

- 切块与全文索引在同一步落库（`chunked` 起关键词就查得到），向量在 `embedding`
  末尾落库，而**阶段推进是之后再写的一次更新**。中间那一瞬（或进程正好在两次写入之间
  被杀）会让一份**已经能检索**的文档停在 `embedding`。
- 所以：MCP 的 `get_document_status` / `list_documents` 直接给你一个算好的
  **`searchable`**（有切块且未停用）；REST 的文档详情没有这一位，
  你可以用同样的口径自己判：**`chunk_count > 0 且 disabled == false`**。
- 宁可高估也不低估：高估的代价是搜一次没命中、如实说"库里没有"；
  低估的代价是**你根本不去搜**。

**搜不到时的处理顺序**（别急着说"没有这份资料"）：

1. 库是不是空的？（先 `GET /knowledge-bases` / MCP 的 `list_knowledge_bases`）
2. 文档处理完了吗？（`GET /documents/{id}` 的 `stage` / `chunk_count`，
   或 `GET /documents/{id}/timeline` 看每一步耗时与失败在哪一步）
3. 有没有失败 / 取消？（`failed` / `canceled` 可 `POST /documents/{id}/reprocess` 重跑）
4. 都正常还不命中，才说"资料里没有"，或者换个说法再查
   （检索对词面与向量都敏感："眼轴监测"与"监测眼轴长度"可能排得不一样）。

### 7.2 删除：原文进回收站，**向量立即清除**

- `DELETE /documents/{id}`：原文进回收站保留 **7 天**（可通过
  `POST /trash/{trash_id}/restore` 恢复，**恢复需要重新摄入**），
  但**切块与向量立即清除——删完立刻搜不到**。
- 删除响应里给了 `trash_id` 与 `restorable_until`，用它们做"可撤销"的界面提示，
  别把它说成"随时能撤"。
- 删库是**不可恢复**的；删之前可以先看影响面：`GET /documents/{id}/impact`、
  `GET /knowledge-bases/{id}/impact`。
- 另外一条更温和的手段是**停用**：`PATCH /documents/{id}/disabled` 后不参与检索，
  但其余一切保留。

### 7.3 检索返回原文，**不生成答案**

- 服务端只回片段与元信息。**别把片段当答案**：你的 Agent 要基于片段自己组织语言，
  并且**每条结论都指回文档名（有页码 / 标题路径就给上）**。
- 片段支撑不了答案时，**如实说"知识库里没有覆盖这个"**——那是一个有用的答案。
- 不要把一般知识伪装成库里的资料（用户问自己的文档，正是因为一般知识不是重点）。

### 7.4 库里没有的东西，检索不出来

这是最常见的一类误判。检索**按库过滤**，一个不含该资料的库，
查询写得再好也不会回东西。所以标准工作流是：
**先列库 → 再按库检索**；也确实要全查时，MCP 的 `search` 可以留空 `knowledge_base_ids`
（= 查这个调用者能看到的全部库），REST 那边则要先把 id 全列出来再传。

### 7.5 注册数据源不会立刻抓取

`add_data_source` / `POST /knowledge-bases/{kb_id}/data-sources` 只是**登记**，
内容要等定时任务，或显式触发一次拉取（`POST /data-sources/{id}/sync`，
`wait=true` 表示立刻做完）。

### 7.6 笔记 ≠ 入库（**这一节已随 Agent 侧拆除**）

`create_note` / `attach_note_to_kb` 属于 **Agent 域**：它们动的是笔记与知识库两个池子，
而笔记那一侧的实现在 2026-10-09 的后端瘦身里整体拆除了。所以：

- 这个服务的对外面上**没有**这两个工具（§9.1 那张表里没有它们）；
- 想把一份内容变成可检索的文档，直接走 `upload_document`（MCP）或
  `POST /knowledge-bases/{kb_id}/documents`（REST）——那条路本来就在，
  而且它就是笔记入库当年复用的同一条摄入链路。

> 记忆（`recall` / `remember`）与检索是**两个池子**，本服务对外面同样不含它们。

### 7.7 一些量级与语义上的细节

| 细节 | 说明 |
|---|---|
| `score` vs `similarity` | 前者是融合分（随名次走），后者才是余弦相似度；界面上别把融合分显示成"相似度" |
| `distribution`（MCP 的 `search`） | 这批命中的分布：`fit`（`strong` / `weak` / `none` / `unknown`）+ 建议 `keep` / `min_score` / `per_doc`；`fit=none` 时**如实说资料里没有**，别拿噪声编答案。注意这三个参数**今天在 MCP 通道上会被丢掉**（见 §3.5），要真按分布收敛请走 REST |
| `filtered_out` | 被阈值 / 筛选 / 人工禁用剪掉的条数——它不为 0 说明"剪过"，不是"只剩这么多" |
| 未标定的嵌入模型 | `min_vector_score` 不传时按模型标定默认；**没标定过的模型默认不设限**（宁可少拦，也不拿别的模型的尺度拦真命中） |
| 开发用嵌入 | 响应里的 `embedding_is_development=true` 表示这次检索**不代表真实效果**，要如实显示 |

## 8. 错误信封与状态码

所有非 2xx 响应都是同一个形状（**程序按 `code` 分支，不要解析 `message`**——
它是给人的中文说明，措辞可能改）：

```json
{ "code": "not_found", "message": "文档不存在：doc_abc123" }
```

| `code` | 含义 | 典型 HTTP |
|---|---|---|
| `invalid_request` | 参数不合法、状态不允许、逻辑前置不满足 | **422**（字段校验）/ **400**（请求形状对、内容与事实对不上） |
| `not_found` | 目标不存在 | 404 |
| `conflict` | 与现有状态冲突（键被占、重名、幂等键处理中） | 409 |
| `unauthorized` | 缺少凭据或凭据无效 | 401（带 `WWW-Authenticate: Bearer realm="kylab"`） |
| `forbidden` | 身份有效但无权做这件事（含超出密钥的库范围） | 403 |
| `unsupported_content` | 这个东西现在拿不到（还没解析完 / 格式不支持） | **409**（见下方说明） |
| `payload_too_large` | 上传内容超过限额 | 413 |
| `upstream_error` | 上游（模型、解析服务、被订阅的站点）失败 | 502 |
| `service_unavailable` | 这个部署现在没有这个能力（缺配置 / 缺签名密钥等） | 503 |
| `knowledge_base_unavailable` | 知识库提供者当前不可用 | 503 |
| `internal_error` | 未预期的服务端错误 | 500 |

**为什么区分 `conflict` 与 `invalid_request`**：前者是"现在不行，重试或换个名字也许行"，
后者是"这个请求本身就不对"。混成一个码，调用方只能靠猜。

**为什么不用 HTTP 状态码表达一切**：`409` 分不清"幂等键被占"和"同名冲突"，
而这两种情况的处理方式完全不同。

> **一处规范与实现不一致，照代码走**：《API 接口规范 v0.1》§1.3 的表里把
> `unsupported_content` 写成 422，而实现里是 **409**。接入方请**按 `code` 分支**，
> 别按状态码——两处口径不同的地方以代码为准。这条已登记，见 §10。

**鉴权相关的固定行为**：

- 缺凭据 → `401`（`unauthorized`），文案给出"该带哪个头"。
- 凭据无效 / 已撤销 → `401`。错误文案**不区分**"前缀不对""长度不对""库里没这条"
  ——区分开等于给攻击者一个布尔预言机。
- 凭据有效但越权 / 只读档做写操作 → `403`（`forbidden`）。
- 本服务**没有"未启用鉴权"这条支路**（唯一例外是本机 `local` 部署档，
  那是 Agent 自己的形态，不是对外接入面）。

**MCP 上的错误形状不一样**（重要）：工具执行时的领域错误会被包成
**一段 JSON 文本**返回，形状是 `{"error": "<原因>"}`，而**不是** MCP 协议错误。
你的客户端要读这个字段来判断成败。

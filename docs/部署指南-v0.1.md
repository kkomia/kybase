## 1. 服务拓扑

知识库服务不是"一个进程"：它由**一个后端 + 三处存储**组成，前端只是外壳。

```
                    ┌──────────────────────────────┐
   浏览器 / 管理台 ──►│ 前端（nginx：静态产物 + /api 反代）│
                    └──────────────┬───────────────┘
                                   │ 同源 /api/v1（无 CORS 问题）
                    ┌──────────────▼───────────────┐
   Agent 侧（kylab）──►│ 后端（FastAPI + 内嵌队列消费者）  │
   MCP 客户端 ────────►│  uvicorn app.main:app :8000   │
   Skill 脚本 ───────►│                              │
                    └──┬────────┬──────────┬────────┘
                       │        │          │
          PG + pgvector│        │对象存储   │DuckDB
     元数据/向量/全文  │        │原件/md/图 │表格副本
                       ▼        ▼          ▼
              PostgreSQL 17   S3/MinIO    <data_dir>/tabular.duckdb
              （硬依赖）      或本地目录    （单文件、单写者）
```

| 组件 | 角色 | 是否必需 | 出处 |
|---|---|---|---|
| PostgreSQL + **pgvector** | 元数据 + 向量（HNSW）+ 全文（tsvector） | **必需**。未配 `KYLAB_DATABASE_URL` 时**启动即失败**，没有降级实现 | `kylab docs/规范/部署与运行-v0.4.md` §2.0、§4.1；`backend/app/core/storage.py:268-273` |
| 对象存储 | 原件（内容寻址）、Markdown 产物、图片 | 可选：留空 `KYLAB_S3_*` 时落本地 `KYLAB_DATA_DIR` 下的 `originals/` `markdown/` `images/` | `backend/app/core/storage.py:89-123`；`config.py:160-166` |
| DuckDB | 表格型文档的结构化副本，与主库物理分离 | **必需（隐含）**：`app/core/storage.py` **无条件**构造它，缺依赖则 `import app.main` 就崩 | `backend/app/core/storage.py:280-291`；`backend/Dockerfile:36-45` |
| 后端（FastAPI） | 摄入流水线 + 检索 + Wiki + 表格 + 账号 + MCP | 必需 | `backend/app/main.py` |
| 内嵌队列消费者 | "上传之后文档会不会被处理"的关键，跟着后端进程起 | 默认开（`KYLAB_RUN_WORKER=true`） | `backend/app/main.py:77-91`；运行规范 §2.3 |
| 前端（管理台） | 知识库页面群 + 登录；由 nginx 发静态产物并把 `/api` 反代到后端 | 可选但推荐（Wiki / 目录 / 分享 / 处理时间线 / 检索分数**没有 MCP 工具对应物**） | `kylab frontend/nginx.conf`；剥离方案 §5.4 形态 C 那段 |
| MCP server | stdio + Streamable HTTP，**只该暴露 KB 工具** | 可选（外部 Agent 接入用） | `backend/app/mcp_server/server.py`；剥离方案 §7.5 |

> 下文所有不带仓库前缀的相对路径（`backend/app/...`、`deploy/...`、`frontend/...`）都指
> **kylab 仓**（`E:\gitlab\kylab`，只读）；本仓自己的文件一律写成 `docs/...`、`frontend/...` 并显式说明。
> 「运行规范」= kylab `docs/规范/部署与运行-v0.4.md`；「剥离方案」= 本仓根目录
> `kylab知识库剥离方案-v0.1.md`；「交接文档」= `docs/交接文档-v0.1.md`。

**三个"硬依赖"的成因**（不是配置疏忽，是设计取舍）：

- PG 必填：v0.12 起 SQLite 退役，PG 是唯一元数据/向量/全文真相源；宁可启动第一秒失败，也不留
  "没配就悄悄退回本地文件"的后路（`storage.py` 模块头）。
- DuckDB 必装：`app/core/storage.py` 在装配时无条件建表格副本，所以 `uv sync` 少装 `tabular` extra
  → 容器连 `import app.main` 都过不去（`backend/Dockerfile:36-45`）。
- 消费者要开：关掉它，上传的文档只会排队，界面上表现为"卡住不动"（运行规范 §2.3、§4.1）。

| 凭据 | 一个**云端解析节点 token**（可选但强烈建议，见 §5.3 首次启动第 3 步）：MinerU / PaddleOCR | `config.py:226-228`；`.env.example` 末段 |
| 容量与并发 | **给不出推荐并发数**：官方规范明确说该项未实测，且"编一张表出来比不给更糟" | 运行规范 §5 |

## 3. 配置项

配置**分两级**，这一条必须记住（`config.py` 模块头）：

- **引导级**：连不上就起不来的东西（数据库连接串、对象存储凭据、数据目录）。**只能来自环境变量**——
  "把数据库连接串存进数据库"是鸡生蛋。
- **运行期级**：可以在网页上改、改完即刻生效的东西（解析节点 token、模型注册、推荐问题开关）。
  落 `app_settings` 表，带掩码、不回显明文。三层优先级：**库 > `.env` 引导值 > 代码默认**
  （`services/runtime_config.py` 模块头）。

### 3.1 归属标注

「归属」一列按《kylab 知识库剥离方案》§3.1 的切分线标注，供剥离落地后各自部署时对照：

- **KB 专用**：归知识库服务；
- **共享**：两侧各一份、各自演化（`docs/交接文档-v0.1.md` §4.4）；
- **Agent 侧**：今天与 KB 同处一个进程，剥离后**不归 kybase**。

### 3.2 引导级环境变量（`KYLAB_` 前缀，只能来自环境变量 / compose / `.env`）

**服务与数据目录**

| 变量 | 默认 | 归属 | 说明 |
|---|---|---|---|
| `KYLAB_DEPLOYMENT` | `server` | 共享 | `server` / `local` 两档，**只在进程启动时定一次**，运行期换不了。KB 服务固定 `server` |
| `KYLAB_DATA_DIR` | `./data` | 共享（各部署一份） | **最大共享耦合点**：它派生出所有存储路径（见 §6） |
| `KYLAB_HOST` | `127.0.0.1` | 共享 | 容器里由启动命令的 `--host 0.0.0.0` 覆盖 |
| `KYLAB_PORT` | `8000` | 共享 | 同上，由 `--port` 覆盖 |
| `KYLAB_CORS_ORIGINS` | `http://127.0.0.1:5173` | KB 专用 | 逗号分隔；走 nginx 同源反代时用不到，直连后端时需要 |
| `KYLAB_SLOW_QUERY_MS` | `500` | KB 专用 | 超过该耗时的**检索**留一条 WARNING |
| `KYLAB_FRONTEND_DIST` | 空 | Agent 侧 | 桌面壳取前端产物的目录；**KB 管理台由谁托管未定**（待 kybase 实现落地后核实） |

**存储后端（KB 专用）**

| 变量 | 默认 | 说明 |
|---|---|---|
| `KYLAB_DATABASE_URL` | 空 | **必填**。`postgresql://用户:口令@主机:5432/库名`。启动时校验连通性、`vector` 扩展与 schema 版本，失败即退出 |
| `KYLAB_S3_ENDPOINT` | 空 | 形如 `http://minio:9000`。**留空 = 落本地文件系统** |
| `KYLAB_S3_ACCESS_KEY` / `KYLAB_S3_SECRET_KEY` | 空 | 配了端点却缺凭据 → **启动即失败**（不允许半配） |
| `KYLAB_S3_BUCKET` | `kylab` | 桶名 |
| `KYLAB_S3_REGION` | `us-east-1` | MinIO 不校验，但 S3 SDK 需要非空值 |
| `KYLAB_S3_SECURE` | `false` | 容器内网互通为假（MinIO 默认 http） |
| `KYLAB_S3_PREFIX` | 空 | 桶内 key 前缀，一个桶放多套环境用；留空即桶根 |

**鉴权（KB 专用，随 KB 走）**

| 变量 | 默认 | 说明 |
|---|---|---|
| `KYLAB_URL_SIGNING_SECRET` | 空 | 签名下载 URL 的密钥。浏览器里 `<img>` 与下载链接带不了 `Authorization` 头。**留空也行**：首次 `POST /auth/setup` 会自动生成一条落库 |

> **没有鉴权开关**：v0.11 起鉴权永远生效，原先的 `KYLAB_AUTH_ENABLED` 与 `KYLAB_CONSOLE_TOKEN`
> **已取消**——"还没配凭据"与"忘了配凭据"在代码上无法区分，于是"没配就放行"等于"无账号即裸奔"
> （`config.py:209-215`、`.env.example:71-91`）。
> **忘记密码没有 HTTP 应急入口**（`deploy/docker-compose.yml:147-149`）。

**任务消费者（KB 专用）**

| 变量 | 默认 | 说明 |
|---|---|---|
| `KYLAB_RUN_WORKER` | `true` | 单容器部署**要留着它**，否则上传后没人处理队列 |
| `KYLAB_WORKER_LEASE_SECONDS` | `60` | 租约时长：worker 执行期间按 1/3 周期续租，崩溃后由超时回收兜底 |
| `KYLAB_WORKER_CONCURRENCY` | `1` | 同进程消费者个数（1–8）。摄入绝大部分时间在**等远端**，加到 2–4 能把等待重叠；上限 8 是跟着连接池（默认 `max_size=10`）走的 |

**解析与向量化行为参数（KB 专用）**

| 变量 | 默认 | 说明 |
|---|---|---|
| `KYLAB_MINERU_TOKEN` | 空 | MinerU 云端解析凭据（KB 专用，属"只登记不收编"那一类，见下） |
| `KYLAB_PADDLEOCR_TOKEN` | 空 | PaddleOCR 云端解析凭据（**KB 专用**） |
| `KYLAB_MINERU_DAILY_PAGE_QUOTA` | `1000` | MinerU 每日优先额度页数。超了**不是报错，是降级排队**，表现为"卡住不动"，所以负载面板显示"今日已用 / 额度" |
| `KYLAB_QUESTIONS_CONCURRENCY` | `4` | 分段出题同时发几批。实测一份 400 段的文档有 50 批、每批 1–2 分钟，串行会堵死后面所有排队文档 |
| `KYLAB_EMBEDDING_BATCH_SIZE` | `32` | 单次 embedding 请求的文本条数 |
| `KYLAB_EMBEDDING_PROTOCOL` | `openai` | `openai` / `wemm`。**只是 `.env` 引导值**，网页上改过之后以库里为准 |
| `KYLAB_DEV_EMBEDDING` | `false` | 开发用确定性（哈希）嵌入，**生产不要开**。关着时"没配嵌入模型"就是真没配：建库被拒、向量通道跳过 |
| `KYLAB_LLM_TEMPERATURE` | `0.3` | 生成式（摘要 / Wiki / 建议问）的采样温度 |
| `KYLAB_LLM_ENABLE_THINKING` | `true` | 思考开关，默认开（主流模型默认都思考） |
| `KYLAB_LLM_THINKING_EFFORT` | `medium` | `low` / `medium` / `high`，按供应商方言翻译或丢弃 |

> **两个 token 是 KB 专用项，且只登记、不收编**：`mineru.token` / `paddleocr.token` 属于
> `SECRET_KEYS`，设置页只回显掩码；它们**没有**被收编进系统钥匙串（`runtime_config.py` 的
> `KEYCHAIN_SETTING_KEYS` 只有 `web.search_api_key` 一个），所以继续走库与 `.env`
> （`runtime_config.py:67-82`）。MinerU token **有效期 90 天且不可续期**，设置页会提示过期。
>
> **模型身份（embedding / LLM 的地址、密钥、模型名、维度）不在环境变量里**：它们统一由
> **模型注册表**承担（`/api/v1/model-registry`），因为"用哪个模型"只该有一个登记入口。
> 后果是**部署完必须去登记一个嵌入模型，否则建库会被拒**（`config.py:252-265`、`.env.example:99-102`）。
> 维度建议填 **≤2000**（推荐 1024）：pgvector 的 HNSW 最多 2000 维，超了就没有向量索引、
> 检索走精确扫描（`.env.example:107-128`）。

**日志（共享）**

| 变量 | 默认 | 说明 |
|---|---|---|
| `KYLAB_LOG_LEVEL` | `INFO` | 控制台与文件**共用一档**，不分开配 |
| `KYLAB_LOG_MAX_SIZE` | `5mb` | 认 `512k` / `5mb` / `1g` / 纯字节数。**写错的值回落到默认并留一条 warning**，不影响启动 |
| `KYLAB_LOG_MAX_BACKUPS` | `3` | 留几份备份 |

> 文件日志在 `<data_dir>/logs/kylab.log`（滚动 5 MiB × 3 份），启动时挂载；写不出来只警告、
> 不拦启动。文件行里带**相对路径:行号**，grep 出来的那一行能直接定位到代码。
> Windows 上文件被日志查看器打开时轮转失败，处置是"这轮不轮转、接着写"，不丢日志（运行规范 §2.1）。
> 注意后两项**不在 `Settings` 上**（`Settings` 是 `extra="ignore"`，未知变量会被静默吞掉），
> 而是 `app/core/logging.py:50-51` 直接读环境变量。

**以下变量今天与 KB 同处一个进程，但按归属表属 Agent 侧——剥离后不归 kybase**

`KYLAB_LOCAL_DB`、`KYLAB_SERVER_URL`、`KYLAB_TOKEN`、`KYLAB_KB_URL`、`KYLAB_KB_TOKEN`、
`KYLAB_DEVICE_ID`（本机档与知识库提供者客户端）、`KYLAB_BACKUP_BUCKET` / `KYLAB_BACKUP_PREFIX` /
`KYLAB_BACKUP_KEEP` / `KYLAB_BACKUP_QUOTA_BYTES`（备份全套，2026-10-08 拍板归 Agent/本机侧）、
`KYLAB_MEMORY_ENABLED` / `KYLAB_MEMORY_WORKSPACE`（长期记忆）、`KYLAB_CHAT_MODE`（对话行为档）、
`KYLAB_GITHUB_TOKEN`（技能市场）、`KYLAB_SKILLS_DIR`（技能目录）。
出处：`config.py:100-158`、`:177-207`、`:287-318`；`docs/交接文档-v0.1.md` §5。

### 3.3 运行期级配置（落库、网页可改）

分组与字段定义在 `kylab backend/app/services/runtime_config.py` 的 `SETTING_GROUPS`，
前端设置页按这个结构渲染，不硬编码字段名。密钥一律只回显掩码，写入留空表示"不改动"。

| 分组 / 键 | 归属 | 说明 |
|---|---|---|
| `mineru.token` `mineru.endpoint` `mineru.model_version` | KB 专用 | 云端解析节点，token 为密钥 |
| `paddleocr.token` `paddleocr.model` `paddleocr.endpoint` | KB 专用 | 同上 |
| `embedding.batch_size` `embedding.protocol` | KB 专用 | 向量化行为参数 |
| `retrieval.floor_score`、`retrieval.baseline_score`、`chat.top_k`、`chat.section_chars`、`chat.material_chars` | KB 专用 | 检索阈值与片段预算 |
| `ingest.summary_enabled` | KB 专用 | 摄入后是否自动摘要 |
| `llm.*`（温度 / 思考开关 / 强度） | 共享 | 两份拷贝、各自演化；KB 侧生成式改成直连 `llm.py` |
| `chat.mode` `chat.permission` `chat.compress*` `chat.context_window` | Agent 侧 | 对话行为 |
| `sandbox.*`、`web.search_provider`、`web.search_api_key` | Agent 侧 | 沙箱与联网搜索 |
| `memory.*`、`provider.backup.*` | Agent 侧 | 记忆与备份提供者 |

> **今天在 KB 服务这一档，运行期配置没有 HTTP 写入口**：`/api/v1/settings` 只挂在**本机档**的白名单上
> （`kylab backend/app/api/v1/router.py:197`），服务器档的会话面 / 设置面已在 2026-10-04 的那一轮退役
> （同文件模块头）。所以 `mineru.token` 这类值今天有两条落地路径：**写进 `.env` 引导值**（推荐），
> 或库里 `app_settings` 里已有的行。
> 而 `/api/v1/model-registry` 在**两个档都挂着**（`router.py:152` 与 `:199`），所以嵌入模型的登记
> 走 HTTP/管理台是通的——建库要选嵌入模型，这一步不能省。

### 3.4 compose 层变量（不是应用配置，写进 `deploy/.env`）

| 变量 | 默认 | 说明 |
|---|---|---|

## 4. 两种部署形态

### 4.1 形态一：干净机器一键 compose

定义在 `kylab deploy/docker-compose.yml`（`name: kylab`，5 个 service）：

| service | 干什么 | 关键点 |
|---|---|---|
| `postgres` | `pgvector/pgvector:pg17-trixie` | `shm_size: 256mb`（PG 并行查询要共享内存，默认 64MB 偏小）；**不对外暴露 5432**，只给 compose 网络内的后端用；`PGDATA` 显式指定，避免数据落进匿名卷 |
| `minio` | `minio/minio:latest` | 控制台与 S3 API 端口**只绑 `127.0.0.1`** |
| `minio-init` | 一次性建桶 | `mc mb --ignore-existing` 建两个桶（知识库桶 + 备份桶），两条都幂等；**缺备份桶不阻塞启动** |
| `backend` | 后端镜像 | 构建上下文是**仓库根**（镜像里要装仓库自带的 `skills/`）；`depends_on` 两个存储的 `service_healthy`；**不直接暴露 8000** |
| `frontend` | nginx 发静态产物 + `/api` 反代 | `depends_on: backend(service_healthy)`——否则首屏先看到一个 502，用户以为部署失败；宿主端口 `${KYLAB_HTTP_PORT:-8080}` |

```bash
cd <kylab 仓>
export KYLAB_URL_SIGNING_SECRET=$(openssl rand -hex 24)
docker compose -f deploy/docker-compose.yml up -d
# 界面 http://localhost:8080 —— 首次打开会让你创建管理员账号
```

**架构上的三个决定**（运行规范 §3.1，照做即可，别改）：

1. **不直接暴露后端端口**：所有流量从 nginx 进，避免"一半请求带 `X-Forwarded-*`、一半不带"的排查噩梦；
2. **前端由 nginx 提供并反代 `/api`**：同源就没有 CORS 问题——生产上配错 CORS 是"本机好用、部署后全 401"的常见来源；
3. **`/api/` 反代关掉缓冲**（`proxy_buffering off`）：对话是 SSE 流式，缓冲会让用户等整段回答写完才看到第一个字（后端也发了 `X-Accel-Buffering: no`，两边都要）。

**验证状态（照规范原文口径）**：`postgres` 服务已按这份定义在真实部署服务器上跑通
（PG 17.11 + pgvector 0.8.6，HNSW + KNN 实测可用，schema 由应用自检引导成功）；
**"整份 compose 在干净机器上一键起"仍未验证**（开发机没有 docker）。
首次在有 docker 的机器上跑，**预期的失败点**是三条：`uv sync` 在 `python:3.12-slim` 里可能缺编译工具
（归因于 `sqlite-vec` 的那条已不成立，该依赖随 SQLite 一并删除，保留这条只是因为没实测过）；
卷权限（容器内以 uid 10001 运行，宿主机 bind mount 时要 `chown 10001`）；
首启健康检查的 20s `start_period` 在慢盘上可能不够（运行规范 §3）。

### 4.2 形态二：NAS / 已有 PG+MinIO 的机器（接外部存储层）

定义在 `kylab deploy/nas/docker-compose.yml`（`name: kylab-app`）。它**不含存储层**——
这台机器上 PG 与 MinIO 早就跑着了，各自有自己的目录与管理方式；这份 compose 只加入同一个
docker 网络（`1panel-network`，`external: true`），**按容器名**连过去，不改存储层配置、不占宿主机端口。

| 与形态一的差别 | 这一份怎么做 | 为什么 |
|---|---|---|
| 项目名 | `kylab-app`（不是 `kylab`） | compose 按项目名管容器，与存储层同名的话 `docker compose up` 会把对方那份的容器当成"多余的"停掉 |
| 运行用户 | `user: "1000:1001"`（宿主机用户），不是镜像里的 10001 | 10001 需要 `chown 10001` 才能写 bind mount；换成宿主 uid 后 `/data` 直接可写。**仍然是非 root** |
| `HOME` | `/data` | 非 root 且 HOME 指向镜像里那个 10001 的家目录时，任何"往家目录写"都会失败 |
| 数据落点 | bind mount `/vol1/1000/docker/kylab/data:/data` | DuckDB 表格副本 + 日志 + 未配 S3 时的原件回退 |
| 界面端口 | `8081` | 这台机器上 8080/8000 都被别的应用占了 |
| 构建源 | `UV_INDEX_URL=阿里云`、`NPM_REGISTRY=npmmirror` | 这台机器到境外带宽不可用（实测 `uv sync` 卡在下载里 700 秒） |

```bash
cd /vol1/1000/docker/kylab/app
docker compose up -d --build        # 构建并起（首次约几分钟）
docker compose logs -f backend      # 看后端日志
docker compose ps                   # 状态（backend 应显示 healthy）
docker compose down                 # 停掉（**不动存储层**）
```

**三条踩过的坑**（`deploy/nas/README.md`）：

1. **`backend/` 改了必须重建后端**。`update-frontend.sh` / `deploy-from-windows.sh` **只重建前端**——
   用它们部署后端改动会得到"页面是新的、后端还是老的"：页面 200、没有报错，但新接口 404 或行为照旧。
   后端变了就整棵重建：`docker compose build && docker compose up -d`。
2. **解包覆盖会留下旧文件**。NAS 的 `src/` 是 `git archive` 解开的**累积**目录，`tar --overwrite`
   只覆盖、不删；Vue 时代的测试文件曾让 `pnpm build` 的 tsc 报错、构建直接失败。换代码时**干净重解**
   （先 `mv src src.bak-$(date +%Y%m%d-%H%M%S)`）。`src/` 里没有任何"只存在于 NAS"的东西，改名备份是安全的。
3. **别只以"页面 200"自证部署成功**。那次 200 完后端却还是老的。更硬的自证是进容器问一句代码事实，
   例如 `docker compose exec -T backend python -c "..."`（`deploy/nas/README.md`「部署完的自证」）。

> **与开发环境共用存储的后果要清楚**：这台 NAS 上的实例与开发实例可能看到**同一份数据**
> （同一个库 `kylab`、同一个桶 `kylab`）。两边都开 `KYLAB_RUN_WORKER=true` **不会重复处理任务**
> （队列靠租约认领），只是有一份冗余；要让部署实例单独一份数据，改 `KYLAB_PG_DB` 与 `KYLAB_S3_BUCKET`
> （那两个库/桶要先建好）。

### 4.3 本地 venv 路线（开发与排障，已实测）

```bash
# ① 先备一个 PostgreSQL（必选）
docker run -d --name kylab-postgres -p 5432:5432 \
  -e POSTGRES_PASSWORD=kylab-dev-secret -e POSTGRES_DB=kylab \
  pgvector/pgvector:pg17-trixie

# ② 后端
cd backend
uv sync --all-extras                     # 注意 --all-extras，见下
cp .env.example .env                     # 至少填 KYLAB_DATABASE_URL；.env 不入库
uv run uvicorn app.main:app --reload     # http://127.0.0.1:8000

# ③ 前端（kylab 那份，端口 5173）
cd frontend && pnpm install && pnpm dev
```

**为什么必须 `--all-extras`**：`app/core/storage.py` 会**无条件**构造 DuckDB 表格副本，而 duckdb 在
`tabular` extra 里——它看着像可选项，其实是组合根的必需项；`parsers` extra（pypdf / pymupdf /
python-docx / openpyxl / pandas）是"上传 → 解析 → 入库"主链路要用的，代码里惰性导入，
缺了只是该功能不可用——但跑产品就该装上；`mcp` extra（`mcp>=2`，SDK 必须是 2.x，1.x 里那个类叫
`FastMCP` 且没有 `add_tool`）只在跑 MCP Server 那个入口时需要。一句话：**跑产品就 `--all-extras`**，
三项一起装掉（运行规范 §2.1、`backend/README.md:13-16`、`backend/pyproject.toml:42-88`）。

开发前端要从别的电脑访问：`vite.config.ts` 里已写 `server.host: '0.0.0.0'`，
**别加 `--host 127.0.0.1`**（命令行参数会盖掉配置，现象是"本机能开、别的电脑连不上"）；
后端不用跟着暴露（`/api` 是开发服务器替浏览器去请求的）；外机连不上先查 Windows 防火墙。

## 5. 首次启动与 schema 自检

### 5.1 启动时会发生什么（`build_stores`，幂等）

顺序与失败点都在 `backend/app/core/storage.py:244-291`：

1. 建 `KYLAB_DATA_DIR` 与本地对象存储子目录（`originals/` `markdown/` `images/`，仅本地实现时）；
2. 对象存储：配了 S3 端点则**构造时 `head_bucket` 校验桶可达**——配错了在启动时炸，不在第一次上传时炸；
3. PG：连接 → `prepare()` = `ensure_schema()` + `check_extensions()`；
4. DuckDB：`<data_dir>/tabular.duckdb`。

**schema 由应用拥有，不需要人工 psql**（DDL 的唯一属主是应用）：空库执行基线 DDL，
已有 schema 则按序补缺的增量迁移。`BASELINE_VERSION = 1`、当前 `SCHEMA_VERSION = 17`
（`backend/app/storage/postgres_impl/schema.py:44-51`）。

**只升不降**（两条都不含糊）：

- 库版本**低于**基线 → 报错，让你去执行 `schema.sql`；
- 库版本**高于**应用已知版本 → 报错：**"库是被更新版应用升过级的，请升级应用而不是降级数据库"**。

每条迁移一个事务、并把版本号写在同一事务里，所以中途失败不会留下"表建了但版本没记"的半截状态；
并发启动的多个副本天然安全（先提交的赢，后一个下一轮跳过）。

### 5.2 起完先跑自检

```bash
# 一条命令查"库到底通不通 / 扩展有没有 / schema 对不对"，不必先起整个应用
#（启动路径上调用的是同一套校验，所以这里通过就意味着应用能起来）
cd backend && python -m app.storage.postgres_impl.validate
# 容器里：
docker compose exec -T backend python -m app.storage.postgres_impl.validate
```

它会打印：连接成功（PG 版本）、pgvector 等必需扩展齐备 + **schema 版本**、public 基础表数、
借一次真实 KNN 往返确认向量能力可用，最后给结论。缺 DSN 时**明确报错退出**，不静默跳过。
缺扩展时它**不会替你 `CREATE EXTENSION`**（那要超级用户，悄悄尝试只会留半截状态），
而是说清"该换镜像还是该装扩展"（`schema.py:529-549`）。

其它探针：

| 打什么 | 期望 | 说明 |
|---|---|---|
| `GET /api/v1/health` | `{"status":"ok","app":"kylab","version":"0.1.1","api_version":"v1"}` | **不鉴权**（容器编排靠它判存活，带鉴权会让探针误判）。上面那个 `version` 是 kylab 单体的；kybase 自己的后端从 **0.1.0** 起，见 §9 第 3 条 |
| `GET /api/v1/docs` | Swagger UI | 接口文档 |
| `GET /api/v1/tasks/health` | `worker_enabled` + 任务健康总览 | 见 §7 的"任务卡住"一节 |

### 5.3 第一次打开界面：五步

1. **建管理员账号**：首次打开界面会进「创建管理员账号」向导（`POST /api/v1/auth/setup`）；
   **在此之前业务接口一律 401**。鉴权没有开关，也没有第二种管理员凭据。
2. **登记嵌入模型**（`/api/v1/model-registry`）：**必须做**。没配嵌入模型时"就是真没配"——
   建库会被拒、向量通道跳过。维度建议 ≤2000（推荐 1024，HNSW 才有索引）。
3. **登记解析节点 token**（可选）：`KYLAB_MINERU_TOKEN` / `KYLAB_PADDLEOCR_TOKEN` 写进 `.env`
   引导值，或库里 `app_settings`。MinerU token 90 天有效期且不可续期。
4. **建库 → 上传 → 看任务中心**：文档处理是**异步**的，上传后要用
   `GET /api/v1/tasks/health` 或任务中心确认消费者在跑；未 `indexed` 的文档搜不到。
5. **建一把 API Key 给外部集成**（`POST /api/v1/api-keys`）：明文只在创建响应出现一次，
   调用时带 `Authorization: Bearer kylab_sk_...`；`permission` 为 `readonly` / `readwrite`，
   `knowledge_base_ids` 留空表示不限制范围。**Agent 侧与 MCP 用的是同一套账号体系**
   （`docs/交接文档-v0.1.md` §5「账号体系随 KB」）。

## 6. 数据目录与备份

### 6.1 `<data_dir>` 里有什么

`data_dir` 派生出**所有**存储路径（`backend/app/core/storage.py` 模块头与 `:71-78`）：

```
<data_dir>/                     容器里是挂载卷 /data
├── originals/                  原件（内容寻址）—— 只在**未配 S3** 时用
├── markdown/                   解析产物（Markdown）—— 同上
├── images/                     图片 —— 同上
├── tabular.duckdb              表格型文档的结构化副本（**单文件、单写者**）
├── logs/kylab.log              文件日志（滚动 5 MiB × 3 份）
└── memory/ 等                  长期记忆 / 技能 —— 属 Agent 侧，剥离后不归 kybase
```

**配了 S3 时，原件与产物在桶里**，`data_dir` 只留 DuckDB + 日志（`storage.py:97-104`）：
本地实现才会去 mkdir 那三个子目录。
本机档（`KYLAB_DEPLOYMENT=local`）另有 `<data_dir>/kylab.db`（SQLite）——**KB 服务不用这一档**。

### 6.2 备份要分三处对待

v0.12 起数据分三处，"拷一个目录"的做法已不适用（运行规范 §6）：

| 内容 | 位置 | 备份方式 |
|---|---|---|
| 元数据 + 向量 + 全文 | PostgreSQL | `pg_dump -Fc`（角色另用 `pg_dumpall --globals-only`）。**不要**直接拷运行中的 PG 数据目录——那是不一致的；要 PITR 再加 WAL 归档 |
| 原件 / Markdown / 图片 | MinIO/S3 桶（或本地 `<data_dir>` 下的 `originals/` `markdown/` `images/`） | 对象的版本化/快照；本地实现则拷目录（对象是只写不改的） |
| 表格副本 | `<data_dir>/tabular.duckdb` | 拷文件（**停服务后**） |

其它两条：

- **回收站**：删除的文档原文保留 7 天（桶内 `.trash/<id>/`），到期由 worker 的空闲维护清理；
  **要立刻释放空间就手动清空该前缀**。注意切块与向量是**立即清除**的，所以删完立刻就搜不到
  （`skills/kylab-knowledge-base/README.md`「三个容易踩的点」）。
- **升级路径**：0.1.0 → 0.2.0 之间存储层换过地基（SQLite → PostgreSQL），**0.1.0 的 SQLite 数据没有
  迁移路径**，只能在 PG 上重新摄入；0.1.0 之后没有别的破坏性变更，同一大版本内升级只需替换镜像/代码，
  schema 自动补齐（运行规范 §6）。

### 6.3 存量库的迁移注意事项（**剥离相关，必须知道**）

现有部署的 PG 已按**交错**序列升到 **v17**——KB 迁移（v2/v4/v8…）与 Agent 迁移（v5/v6/v10/v12/v13…）
连号交错在同一串里。剥离后两边要切成**两条独立连号序列**，而**"不能只照顾新装"**：
要给存量库一条版本映射 / 冻结点路径（2026-10-08 已拍板「走版本冻结点」，
见 `docs/交接文档-v0.1.md` §5、剥离方案 §7.7）。
**切序列之前，别在生产库上试**（硬约束：NAS 部署不动，切割在仓库里做）。

## 7. 常见问题

### 7.1 启动就失败

| 症状 | 原因 | 处置 | 出处 |
|---|---|---|---|
| 启动即失败，提示 `KYLAB_DATABASE_URL` | 没配 PostgreSQL 连接串 | 填上。**这是必填项，没有降级路径**，也不会静默退回本地文件 | `storage.py:268-273`；运行规范 §4.1 |
| `ModuleNotFoundError: duckdb`（`import app.main` 就炸） | `uv sync` 没带 `--all-extras` | 加 `--all-extras`。duckdb 看着像可选 extra，其实是组合根的必需项 | `backend/Dockerfile:36-45`；运行规范 §2.1 |
| 报 `OSError: Readme file does not exist` | 构建时没把 `README.md` 拷进镜像，而 `pyproject.toml` 写着 `readme = "README.md"`，hatchling 装项目自身时要读它 | 镜像里 `COPY backend/README.md`（现有 Dockerfile 已修） | `backend/Dockerfile:39-44`；2026-09-21 在 NAS 上首次实测到 |
| 报缺 `vector` 扩展（psycopg `UndefinedFile` / 58P01） | 用的 PG 镜像里根本没带 pgvector | 换 `pgvector/pgvector:pg17-trixie`。应用**不会**替你 `CREATE EXTENSION`（那要超级用户） | `schema.py:482-485`、`:529-549` |
| schema 版本高于应用 → 拒绝启动 | 库被更新版应用升过级 | **升级应用，不要降级数据库** | `schema.py:495-499` |
| 配了 `KYLAB_S3_ENDPOINT` 却缺凭据 | 半配状态：有端点没钥匙 | 补齐凭据，或清空端点改用本地文件系统。**不允许半配**，否则会变成"上传时才发现" | `storage.py:106-111` |
| `PermissionError: [Errno 13]` 读源码 | 某些文件系统（NAS 的 `/vol1`）把文件报成 000，COPY 原样带进镜像，换了 uid 就不可读 | 镜像里 `chmod -R a+rX /app`（现有 Dockerfile 已有）。**这条与"以哪个 uid 运行"解耦** | `backend/Dockerfile:79-84` |

### 7.2 起来了但队列不动

`GET /api/v1/tasks/health` 给运行态总览；任务列表里每一项也带 `health`。

| 判据 | 含义 | 怎么算 |
|---|---|---|
| `running` | 正常执行中 | 状态 RUNNING 且**租约未过期** |
| `stalled` | **可能卡住了** | RUNNING 但租约已过期——没有 worker 在续约 |
| `overdue` | 该跑没跑 | PENDING 且 `next_run_at` 已过去 10 分钟以上 |
| `idle` | 排队中 | PENDING 且还在正常等待 |
| `done` | 已结束 | SUCCEEDED / FAILED / CANCELED |

| 症状 | 多半是什么 | 怎么办 |
|---|---|---|
| 任务一直 `idle` 排队 | 消费线程没开 | 确认 `KYLAB_RUN_WORKER=true` 并重启 |
| 任务变 `stalled` | 进程崩过 / 被 OOM 杀 | 重启服务；租约过期后任务会被回收重跑 |
| 任务 `overdue` | 同上，或调度没起来 | 看 `/tasks/health` 的 `worker_enabled` |
| 任务反复失败 | 解析器或模型凭据问题 | 看任务详情里的 `error`（含阶段名） |
| 解析忽然变慢 | MinerU 每日优先额度（默认 1000 页）用尽——**不是报错，是降级排队** | 看负载面板的"今日已用 / 额度"；额度是云端政策、会变 |

**为什么用租约过期而不是耗时阈值**：租约是 worker 主动心跳续的，过期就意味着"没人认领这个任务了"
——这是**确定的事实**；而"跑了超过 N 分钟"只是启发式（一份 500MB 的 PDF 解析半小时是正常的），
误报多了就没人看这个标记了（运行规范 §4）。

### 7.3 存储与数据

| 症状 / 风险 | 说明 | 出处 |
|---|---|---|
| **DuckDB 是单文件、单写者** | 表格副本层 `<data_dir>/tabular.duckdb`。**KB 服务要多副本时，这一层必须先改造**——多进程同时写同一个文件不是可选项 | 剥离方案 §7.3、`docs/交接文档-v0.1.md` §4.5-4 |
| 上传大文件被挡 | 三层上限要一致：后端 `MAX_UPLOAD_BYTES = 200MB`，nginx `client_max_body_size 200m` | `backend/app/api/v1/documents.py:64`、`kylab frontend/nginx.conf:14` |
| 上传报错后原文件找不到 | 原件走内容寻址；配了 S3 就在桶里，没配就在 `<data_dir>/originals` | `storage.py:71-75` |
| 表格里的 `007` 变成了 `7` | **不会**：DuckDB 里一切列都是 VARCHAR，刻意不做类型推断（保真比类型重要） | `duckdb_impl/tabular_store.py` 模块头 |
| 向量检索慢、日志说没有索引 | 嵌入维度 > 2000 时 pgvector 建不了 HNSW，走精确扫描。系统**不会假装"索引建好了、只是慢"**——会把那句话写进日志并交给调用方显示 | `.env.example:107-128`、`config.py:252-265` |
| 拷运行中的 PG 数据目录 | **不要**。那是不一致的；用 `pg_dump` 或 `pg_basebackup` | 运行规范 §6 |
| 日志级别改了没生效 | 写错的值会**回落到默认并留一条 warning**——静默用默认值会让"我设了没生效"变成没人能解释的现象 | 运行规范 §2.1 |
| 定时任务在错误的时刻跑 | 容器时区。`TZ` 必须显式设（默认 UTC），cron 按容器本地时间解释 | `deploy/docker-compose.yml:129-132` |
| 容器重建后数据没了 | 数据都在卷里：`kylab-data`（`/data`）、`kylab-pg`、`kylab-objects`；`docker compose down` 不动它们 | `deploy/docker-compose.yml:207-216` |

### 7.4 接入与鉴权

| 症状 | 说明 | 出处 |
|---|---|---|
| 业务接口一律 401 | 还没建管理员账号：首次打开界面进 `POST /auth/setup` 向导 | `deploy/docker-compose.yml:146-149` |
| 忘记管理员密码 | **没有 HTTP 应急入口** | 同上 |
| 外部 Agent 连 MCP 说没权限 | HTTP 模式**强制鉴权**：每个请求带 `Authorization: Bearer <API Key>`；stdio 模式凭据放客户端 `env` 的 `KYLAB_MCP_KEY`。两者都没有则一律拒绝（握手与 `tools/list` 仍放行，工具调用在 `call_tool` 里被拒） | `backend/app/mcp_server/auth.py`、`skills/kylab-knowledge-base/README.md`「安全」 |
| MCP 能列出一堆跟知识库无关的工具 | **现状如此、剥离后必改**：`mcp_server` 会把整张工具表（21 个）挂出去；KB 服务只该暴露 KB 工具，切分依据是 `_KB_TOOLS` 白名单 + `server.py` 的 `_PARAMS` 参数白名单 | 剥离方案 §7.5；`docs/交接文档-v0.1.md` §5 |
| MCP HTTP 监听地址 | 默认 **只监听 `127.0.0.1`**（工具集里含删除）。要局域网开放得显式 `--host 0.0.0.0`，且只放在可信网络里 | `mcp_server/server.py:181-194` |
| 想确认 MCP 装上了 | `cd backend && python -m app.mcp_server.server --list-tools`（一个便于排障的开关）。**别比对记忆里的工具个数**——它随版本变，读它列出来的清单 | `mcp_server/server.py:195-218`；`docs/交接文档-v0.1.md` §3.3 |
| 页面能开但接口 404 | 很可能后端镜像没重建（见 §4.2 第 1 条坑） | `deploy/nas/README.md` |

### 7.5 剥离期专属的坑（读到这里说明你在做剥离）

1. **`KYLAB_DEPLOYMENT=local` 与 `KYLAB_DATABASE_URL` 不许同时出现**：本机档配了连接串
   **启动第一秒就报错**（两个真相源同时在场时"会话写到哪儿"取决于哪段代码先读哪个字段，
   失败形态是**数据被写进错误的库**）。这条校验在 `Settings` 构造期
   （`config.py:320-340`），`build_stores` 里还有一条兜底。
2. **过渡期两个仓库的同一文件以 kylab 为准**，kybase 不回写；`skills/kylab-knowledge-base/`
   处双份并存期，权威在 kylab 侧（`docs/交接文档-v0.1.md` §3.4、§7.3）。
3. **迁移版本号断裂**：见 §6.3，别只照顾新装。
4. **`user_id=None` 共享桶**：裸 API Key 通道建的资源没有归属人。独立 KB 服务若要按用户隔离，
   协议上得补 owner 传递（剥离方案 §7.2）。
5. **MCP 工具面不收就会泄漏**：那份 MCP server 剥离后若不收窄，Agent 工具会从 KB 服务抛出去。

## 8. 过渡形态 vs 目标形态

这一节是本文存在的理由：**别把今天能跑的当成 kybase 已经交付**。

### 8.1 今天（过渡形态）怎么跑

**后端**：跑 kylab 的**服务器档**——它就是今天的知识库服务。

```bash
# 干净机器
cd <kylab 仓> && docker compose -f deploy/docker-compose.yml up -d
# 或 NAS 上接外部 PG/MinIO
cd /vol1/1000/docker/kylab/app && docker compose up -d
```

三点要知道：

- **服务器档今天实质只剩"知识库管理台 + 备份 + 健康"**：会话面端点已从服务器档退役
  （`/chat/stream`、`/conversations/*` 等整族退场，只留 `/conversations/export` 一条只读导出流
  与 `/chat/suggested-questions`）。见 `kylab backend/app/api/v1/router.py` 模块头与剥离方案 §2。
- **它的人格是"单体后端"**：KB 与 Agent 的服务图、`app_settings`、任务队列表、对象存储桶、
  `data_dir` 都还混在一处——所以今天的部署指南里会看到"长期记忆""技能目录""备份桶"这些
  **跟知识库无关**的配置项。剥离后它们不归 kybase（§3.2 已逐项标注）。
- **本仓后端已搬入、尚未切换**：`backend/` 是 kylab `b0685e9` 的整树（**含 Agent 侧代码，
  本轮不瘦身**），`deploy/nas/docker-compose.yml` 也已写好；生产上跑的还是上面那台 kylab 单体。

**前端**：本仓 `frontend/` 的知识库管理台**今天就能跑**，指向上面那台后端即可。

```bash
cd frontend
pnpm install
pnpm dev                                   # http://localhost:5175（5173 是 kylab 前端的，两个能同时跑）
KYBASE_API_TARGET=http://127.0.0.1:8000 pnpm dev   # 指到本机后端；默认是 NAS 上那台（8081）
pnpm build && pnpm preview                 # 生产构建的验收入口（4175）
```

它的页面只有**登录 / 概览 / 所有知识库 / 库详情 / Wiki / 文档详情 / 任务中心 / 404**
（`frontend/src/app/routes.ts` 与 `features/layout/SideNav.tsx` 是同一份清单的两面）——
会话、笔记、记忆、能力、项目那几页**没有搬过来**。

> **今天管理台上没有「设置」页**：模型注册、向量化、解析节点 token 这几项运行期配置
> 在独立管理台上**还没有落点**（`frontend/src` 里没有设置页，只有 `api/modelRegistry.ts` 这个接口层）。
> 今天要改这些，走 kylab 那份界面，或直接打 `/api/v1/model-registry`。
> 这是**待 kybase 实现落地后核实**的一项。

### 8.2 kybase 独立之后会变成什么样（目标形态）

按剥离方案 §5.1 / §6 阶段 3–4 与 `docs/交接文档-v0.1.md` §5 的定案：

| 维度 | 今天（过渡） | 独立之后 |
|---|---|---|
| 后端 | kylab 单体，`KYLAB_DEPLOYMENT=server` 档，KB 与 Agent 同进程、同库、同桶 | kybase 自有镜像与后端进程，只含 KB 域（摄入/检索/Wiki/表格/账号/MCP） |
| 编排 | kylab `deploy/docker-compose.yml`（含 Agent 侧要的备份桶等） | **`kybase/deploy/` 出自己的 compose**——`deploy/nas/docker-compose.yml`（NAS 应用层：backend + mcp + frontend，接外部 PG/MinIO）已落地但**未在 NAS 上实测**；`deploy/docker-compose.yml`（干净机器四件套）仍是自 kylab 搬过来的那一份 |
| 镜像 | `kylab-backend:0.1.1` / `kylab-frontend:0.1.1` | 自有镜像名 `kybase-backend` / `kybase-frontend` 与**独立版本线**——已起在 `0.1.0`（`backend/pyproject.toml`、`config.py` 的 `app_version`、两份 compose 一致，`scripts/check_layering.py` 的 V1 核这一条） |
| 环境变量前缀 | `KYLAB_`（全部） | 是否改成 `KYBASE_`、哪些保留同名，**待 kybase 实现落地后核实** |
| 迁移序列 | 交错一串，当前 v17 | 两条独立连号序列；存量库走**版本冻结点**路径 |
| MCP 工具面 | 整张工具表（21 个） | **只暴露 KB 工具**（`_KB_TOOLS` 10 个 + `_PARAMS` 参数白名单） |
| 账号体系 | 与 Agent 混在一张 PG 里 | **随 KB**（库分享、库范围钥匙、管理员都是 KB 语义的资产） |
| 备份 | 服务器档挂着备份提供者 | **归 Agent / 本机侧**（`BackupProvider` 是与 KB 平行的第二个提供者） |
| 前端 | kylab 壳内也有 KB 页面群；本仓管理台独立一份 | kylab 侧**下线 KB 页面群**，只留「知识库连接」设置与对话内选库/引用；KB 页面群归本仓管理台（纯 web、不进桌面壳） |
| Schema | 应用启动自检自建（`ensure_schema`，只升不降） | 同一套机制（不变），但基线 schema 会重新导出成 KB 服务自己的基线 |

三条**不会变**的（照旧适用本文其余各章）：schema 由应用拥有、只升不降；PG (+pgvector) 是硬依赖；
摄入是异步的，消费者不开就只会排队。
